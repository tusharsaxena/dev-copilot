# CLAUDE.md — dev-copilot plugin

## Purpose & stack

A **Claude Code plugin** (not an application, and not a WoW addon) that ships development helpers for **any** repository and, in the same plugin, the World of Warcraft addon tooling that used to ship separately as `wow-addon`. **One plugin, two profiles:** every command first classifies the repo it runs in (`dev-copilot-profile`), behaves generically in a `generic` repo, and in a `wow` repo (a Ka0s addon, `LibKa0s`, `WowAddonStandards`, or a tooling repo like this one) applies the full Ka0s WoW Addon Standard behavior its `/wow-addon:` predecessor had. Generic runs never load WoW instructions.

What it ships: git diff/commit (opt-in push), documentation drift sync, a measure-first principal-engineer review subagent, test running, gated version bumping, changeset finalization, execution-status reporting (progress, percent complete and time to finish for a conversation's planned work), and the six-command `issue-*` family (discovery, triage, listing, detail, summary, hand-filing) over a GitHub-issue store keyed on `state:` and `severity:` labels — all **shared**. Plus ten **WoW-only** `wow-*` commands: standard-compliant scaffolding, compliance auditing (a second subagent), standards-reference revendoring and cross-repo learning harvesting (the two halves of the standards cycle), LibKa0s re-vendoring and new-surface adoption (the consumer-side half of the *library* cycle — a different cycle, sharing only the word "revendor"), interface bumping, automated-test recording, in-game perf-run analysis, and the CurseForge journal (releases with download counts, and classified comments with an issue hand-off). Two hooks: line endings and bounded runs.

Everything here is **Markdown command/agent/overlay specs + a stdlib-only Python detector, overlay checker and CurseForge journal fetcher + hook scripts (the line-ending hook, and the bounded-runs hook with its Python matcher and `ka0s-bounded` runner) + JSON manifests** — no compiled code, no package manifest. Five unit-test files cover the four Python modules and the line-ending hook.

Current version: **2.3.0** (in `.claude-plugin/plugin.json`). 2.3.0 (CF-10) renders every CurseForge report time in the owner's local timezone (`timezone` in the journal's `journal.config.json`) and the releases report as one Addon / Version / Release Date / Downloads / Changes-since table, derived from the journal so `report-releases` can rebuild it. 2.2.0 adds the CurseForge journal (CF-00..CF-09): `wow-curseforge-releases` and `wow-curseforge-comments`, `scripts/curseforge_journal.py` behind `bin/ka0s-curseforge`, writing only to `Ka0sAddonsCommonTasks/journal/curseforge/`; design `docs/superpowers/specs/2026-10-10-curseforge-journal-design.md`, plan and ledger `docs/superpowers/plans/2026-10-10-curseforge-journal.md`. 2.1.0 is the 2026-10-07 review-and-audit remediation (DC-01..DC-15): the bounded-runs hook no longer denies `command -v` probes and catches `sh -c` and `ulimit -v unlimited` evasions, `ka0s-bounded` kills the whole run on timeout, the line-ending hook resolves symlinks and has its own test, the issue commands give `all` one meaning in a WoW repo, `docs/ARCHITECTURE.md` was added, and the specs point at standard v2.77.0. 2.0.0 was the merge release: dev-copilot 1.0.0 (four generic commands) and wow-addon 2.5.0 (22 commands, 2 agents, 2 hooks, plus unreleased work moving the specs onto standard v2.74.0's sighted complexity suite, `GI-PLUG-01`/`GI-PLUG-01R`) became this one plugin, with wow-addon's history merged in (`--allow-unrelated-histories`, merge `4914203`; its tip is `4914203^2`). The major bump is because every `/wow-addon:<x>` name and the `~/.claude/wow-addon/` state dir changed — both break callers. wow-addon's own 2.x line (the label-based issue store at 2.0.0, `revendor-libka0s` 2.1.0, `execution-status` 2.2.0, the bounded-runs hook 2.3.0, `bin/ka0s-bounded` 2.4.0, the diagnostics dump 2.5.0) lives in the merged history, not in a version number here. Design: `docs/superpowers/specs/2026-10-04-merge-wow-addon-design.md`; plan and execution ledger: `docs/superpowers/plans/2026-10-04-merge-wow-addon.md`. 2.0.1 removed the transitional `~/.claude/wow-addon` support and names `dev-copilot` as the audit rotation's tooling repo.

**This repo ships nothing to the WoW client, so it pins LF** (Ka0s WoW Addon Standard,
`line-endings-§2`). Its root `.gitattributes` carries the non-client canonical body
(`line-endings-§5`) — `* text=auto eol=lf`, the `*.sh text eol=lf` and `*.py text eol=lf` shebang
carve-outs (`line-endings-§3`), binaries marked `binary`. Write LF here. The `*.sh` carve-out is not
decorative in this repo: `scripts/normalize-eol.sh` is the hook Claude Code executes, and a shebang
followed by CRLF makes the kernel look for an interpreter literally named `bash\r`. The same goes for
the extensionless `bin/` wrappers and `scripts/ka0s-bounded` (covered by `* text=auto eol=lf`).

## Repo profiles

`dev-copilot-profile [path]` (default: cwd) prints six `key=value` lines, always in this order: `profile` (`wow`|`generic`), `kind` (`addon`|`library`|`standards`|`tooling`|`generic`), `repo` (git top-level, or the path itself outside git), `name` (basename of `repo`), `root` (the plugin root), `reason` (the rule that matched). Exit code is always 0.

Rules, evaluated at the **git top-level** (so a run from `Foo/modules/` classifies `Foo`), first match wins:

0. **Override** — a `.dev-copilot` file at the repo root with `profile=wow|generic` and, for `wow`, an optional `kind=`. Parsing is forgiving on purpose: blank lines, `#` comments, spaces around `=`, CRLF and case are all tolerated. `profile=wow` with a missing or unknown `kind` means `addon`; an unrecognized `profile` value is ignored and detection falls through to the rules.
1. **standards** — dir name or `origin` URL basename is `WowAddonStandards`.
2. **tooling** — dir name or `origin` basename is `Ka0sAddonsCommonTasks` (the cross-repo workspace the collection's `finalize`, `issue-*` and `wow-revendor-*` runs start from; without the rule it detects as `generic` and those runs lose the collection scope). Being `wow/tooling` does not put the workspace in the audit rotation: `wow-standards-audit`'s table still names it and stops.
3. **library** — dir name or `origin` basename is `LibKa0s`, or a root `LibKa0s.toc`.
4. **addon** — a **root** `*.toc` holding a line that starts `## Interface:` (a nested `.toc`, or one without that line, does not count).
5. **generic** — otherwise.

`root` is derived from the script's own real path, so it works where `${CLAUDE_PLUGIN_ROOT}` is not substituted; the `${CLAUDE_PLUGIN_ROOT}/bin/dev-copilot-profile` form is only the fallback when the bare name is not on PATH. Where a WoW-only command has `kind`-specific behavior (`wow-standards-audit`'s rule-set choice, `wow-harvest-standards`' standards-only gate), it uses the detector's `kind` rather than re-deriving it. Multi-repo flows (`finalize`, the `issue-*` `all` scope, `wow-revendor-*`) run detection **per repo**.

## Overlay contract

- **Step 0 is a verbatim block.** Every shared base (and `agents/review.md`) opens with the identical `## Step 0 — Detect the repo profile` block from the plan, differing only in the overlay filename: run the detector; on `profile=wow`, Read `<root>/profiles/wow/<name>.md` and apply it; on `profile=generic`, follow the spec as written and **do not read the overlay**; when neither invocation of the detector works, treat the repo as `generic` and say so. Command-specific text goes in paragraphs *after* the block, never inside it — e.g. the multi-repo commands (`finalize`, `issue-audit`, `issue-triage`, `issue-details`, `issue-summary`) append a "detection runs per repo" paragraph saying the overlay applies only to a WoW repo's portion of the run. Two deliberate variants: `commands/review.md` only records `profile`/`kind` and passes them to the agent in a `Detected repo profile:` line (the agent re-detects and trusts its own run), and `commands/execution-status.md` detects per repo only to label its report and names no overlay. For every base that has an overlay (commands and `agents/review.md` alike) the checker compares the block word for word against `STEP0_BLOCK` in `scripts/check_overlays.py`, so a wording change is made there and in every base at once; for the two variants and the overlay-less shared commands it checks only that `dev-copilot-profile` appears.
- **Hook markers.** A base marks a hook point with `<!-- overlay: <id> -->` on its own line, directly above what it governs. **Span:** a marker directly above a heading governs that heading's whole section, up to the next heading of the same or higher level; a marker above any other block governs that one block (a paragraph, list, table or code fence). A `replaces` section may state its exact extent in its first sentence — narrower than the span ("Replaces only Step 5's `TODO.md` and `CHANGELOG.md` bullets…"), or wider over the blocks that directly follow, up to the next marker or heading ("Replaces both opening paragraphs of Step 1") — and whenever its extent differs from the span it **must** say so, or the reader drops text the overlay meant to keep (or keeps text it meant to drop). This is wider than the design spec's "may narrow itself"; prefer narrowing, and widen only where moving the marker would split a list from the paragraph that explains it.
- **Overlay files** are a short preamble (optionally a `### How kind changes this overlay` subsection) then sections headed exactly `## <id> — adds` or `## <id> — replaces` (an em dash, U+2014). `## extra — adds` carries WoW-only steps with no generic counterpart and states where in the flow they run. The overlay for agent `X` is `profiles/wow/agent-X.md`.
- **Overlays carry only WoW deltas**, never a copy of generic text — a duplicated paragraph is two places a fix has to land. The flip side is the parity rule: in a WoW repo, base + overlay must reproduce **every instruction** of the `/wow-addon:` spec it came from (`git show wowaddon/master:commands/<x>.md`, or `4914203^2:` once the remote is gone). When editing either half, walk the WoW source section by section and name where each instruction lands.
- **`kind=standards` / `kind=tooling` repos** have no Lua, no TOC and nothing for the addon rules to bind to; overlays say per section which rules are *not applicable* there and fall back to the base's generic step. Keep that explicit in any new overlay rather than letting an addon rule fire on a docs repo.
- **WoW-only commands** open with `## Before anything — confirm this is a WoW repo` (placed before their own Step 0, so the WoW source's step numbering survives): on `profile=generic` print the one refusal line naming the command and the `.dev-copilot` override, and stop. Exceptions that are deliberate: `wow-revendor-libka0s` and `wow-revendor-standards` take their targets from `$ARGUMENTS`, so from a generic cwd they refuse only when no target is named or every named target detects as generic; `wow-new-addon` **never refuses** (the addon does not exist yet) and only warns when the target would nest inside another repo; `wow-bump-interface` stops on a non-`addon` kind; `wow-harvest-standards` runs only at `kind=standards`.
- **`scripts/check_overlays.py`** fails when an overlay has no base, an overlay section names a marker the base lacks, a base marker has no overlay section, a marker or a (non-`extra`) section id appears twice, an `extra` section replaces, an overlay has a `## ` heading that is not one of the two forms, a command/agent mentions a `profiles/wow/<x>.md` that does not exist or is not its own, an overlay-bearing base's Step 0 is not the verbatim block naming its own overlay, or a shared or `wow-*` command lacks `dev-copilot-profile`. It does not check file modes: `core.fileMode=false` on this DrvFs checkout hides them, so set the exec bit of a new script with `git update-index --chmod=+x`. Two footguns follow. Any `## ` heading in an overlay is parsed as a section — use `###` for anything else. And a literal `profiles/wow/<something>.md` written into a spec as an *example* is checked as a reference; spell examples with `<name>` placeholders.

## Entry points & lifecycle

Claude Code auto-discovers `commands/` and `agents/` by directory; there is no registration file listing them. A command file becomes live the moment it exists and the plugin is (re)loaded. `profiles/` is **not** auto-discovered — overlays are plain files a command Reads at run time from the detector's `root`. `bin/` is put on PATH. `hooks/hooks.json` registers both hooks — `PreToolUse(Bash)` for bounded runs and `PostToolUse(Write|Edit|MultiEdit)` for line endings. To activate changes in a session: **`/reload-plugins`** (no restart needed).

- **Command spec** = YAML frontmatter (`description`, `argument-hint`, `allowed-tools`) + a Markdown body that instructs the agent. `$ARGUMENTS` is the user's argument string.
- **Agent spec** = frontmatter (`name`, `description`, `tools`) + body. The `name` becomes `dev-copilot:<name>` when dispatched.

## Configuration & state

- **Config files:** a target repo's `.dev-copilot` override (above). Nothing else is read from the target repo as plugin config.
- **Env vars:** `CLAUDE_PLUGIN_ROOT` (set by Claude Code; used by `hooks.json`, the hook script and the Step 0 fallback); `KA0S_BOUNDED_HOOK=off` (inline, per command) opts out of the bounded-runs hook; the runner reads `KA0S_KIT_PROC_MB`, `KA0S_KIT_TREE_MB`, `KA0S_KIT_TASKS`, `KA0S_KIT_TIMEOUT_S`, `KA0S_KIT_SLOT_MB`, `KA0S_KIT_SLOTS` (README *Hooks* documents defaults), plus the user switches `KA0S_KIT_CGROUP=off` (skip the tree cap) and `KA0S_KIT_GUARD=off` (drop every bound; for a debugger, never a gate) and the internal `KA0S_BOUNDED_DEPTH`; the CurseForge fetcher reads `CURSEFORGE_API_KEY` (the Core API key; it wins over the file below) and `KA0S_CF_JOURNAL` (the journal folder; default `Ka0sAddonsCommonTasks/journal/curseforge` beside the repo at the cwd).
- **State lives under `~/.claude/dev-copilot/`** (moved from `~/.claude/wow-addon/` in 2.0.0):
  - `bin/ka0s-bounded` — the runner symlink the hook maintains.
  - `issue-triage/<scope>-<YYYYMMDD-HHMMSS>.jsonl` — `issue-triage`'s per-run decision journal. It is outside the session on purpose — a scratchpad journal survives a failed API call but not a crashed session, and the journal exists precisely so a decision the user made can be recovered by a *later* run. A journal missing its `complete` line is an unreconciled run, and that is the only signal the resume check uses. No other spec reads or writes it, nothing prunes it automatically, and no command may treat it as a cache of issue state — GitHub is the store, the journal is the record of what was decided.
  - `curseforge.env` — the owner's CurseForge Core API key, as a `CURSEFORGE_API_KEY=` line. `scripts/curseforge_journal.py` reads it **literally**, never by sourcing it, because the key holds `$` characters a shell would expand into a wrong key and a 403. The key is never printed, logged or written to the journal. It is deliberately not named `CF_API_KEY`, which the packager uses for the author upload token.
  - Plus the runner's slot pool at `${XDG_CACHE_HOME:-~/.cache}/ka0s-kit/slots`.
- **No legacy paths.** 2.0.0 shipped transitional support for the retired plugin (the hook also maintained `~/.claude/wow-addon/bin/ka0s-bounded`, `issue-triage` also read `~/.claude/wow-addon/issue-triage/`, and the detector classed a `wow-addon` checkout as `tooling`). All three were removed once the phase-2 ripple left nothing naming them: every surviving journal there carried its `complete` line, and the archived repo needs no profile. Don't reintroduce a second state path.
- **External needs on the machine of whoever runs a command** (not plugin config): `wow-standards-audit`, `wow-new-addon`, `wow-revendor-standards`, `wow-automated-tests` and `wow-perf-analysis` fetch the external **[`WowAddonStandards`](https://github.com/tusharsaxena/WowAddonStandards)** repo at runtime (raw GitHub, needs network), and the WoW review fetches it for its guardrail; the six `issue-*` commands shell out to the **`gh`** CLI (installed and authenticated), and `issue-audit` treats an absent/unauthenticated `gh` as a skipped sweep rather than a failure; `wow-revendor-libka0s` is the exception on the *library*, and for the same reason: it reads the sibling **`LibKa0s`** checkout off local disk rather than fetching, because its payload is bytes (thirty-two `.lua` files as of v1.66.0, an `.xml`, `LICENSE`, and a `media/` subtree of icon TGAs, textures and a font) taken from a **git tag** via `git archive` — no checkout, no run, and no raw-GitHub fallback; it also needs `gh` to file the declines its interview records, and reports an unfiled decline rather than degrading silently. `wow-harvest-standards` is the exception on the *standard* — it runs *inside* the standards repo and reads it from the **working tree** (it is about to edit those files), while reading every sibling addon repo off local disk, so it needs the collection checked out beside it rather than a raw-GitHub fetch, though its closed-issue sweep still goes through `gh` and so still needs network. `wow-curseforge-releases` and `wow-curseforge-comments` need the owner's CurseForge Core API key and network access to `api.curseforge.com` and `www.curseforge.com`, plus the sibling `Ka0sAddonsCommonTasks` checkout that holds the journal and every roster addon's checkout for its TOC project id; the comments command also needs `gh` for the issues it files, and without it skips the hand-off rather than degrading. `run-tests` invokes whatever it detects (generic: npm/pytest/go/cargo/make/…; WoW: **luacheck** and a **Lua** interpreter), treating an absent tool as a skipped suite, not a failure. In WoW repos `wow-standards-audit`, `bump-version`, `review`, `wow-automated-tests` and `wow-new-addon` (its first automated-test bundle) additionally need **`lizard`** for the complexity report, always reached through the vendored runner's sighted complexity suite and never run over a tree by hand (`automated-tests-§3`, standard v2.74.0: raw `lizard` is blind in Lua), and all five treat its absence as *not run / report is stale*, never as a pass or a fabricated number (for `bump-version`, and for `wow-new-addon`'s `v0.1.0` tag, a suite that did not run blocks the release gate rather than passing it) — `review` also re-runs `luacheck` and the addon's Lua suites for the same reason, with the same skip-don't-fabricate rule.

- `python3 scripts/check_overlays.py` — the live tree; prints `OK: 13 overlays`.
- `python3 -c "import json; [json.load(open(f)) for f in ('.claude-plugin/plugin.json', '.claude-plugin/marketplace.json')]"` — both manifests parse.
- `dev-copilot-profile <path>` against a real addon, `LibKa0s`, `WowAddonStandards`, `Ka0sAddonsCommonTasks`, this repo (`wow/tooling`, `reason=override`) and a generic repo.
- `/reload-plugins` to confirm the plugin loads and the counts match (`Reloaded: … plugins · … skills · … agents · … hooks`).
- The line-ending hook's harness is `scripts/test_normalize_eol.py`: each case builds a throwaway git repo with its own `.gitattributes`, pipes the hook JSON into `scripts/normalize-eol.sh` and compares bytes. It covers **both arms** (LF → CRLF and a mixed file → CRLF; CRLF → LF), an already-correct file staying byte-identical in each, a path with no declared `eol`, a file marked `binary` or `-text` **inside a CRLF-pinned repo** — the pin answers `eol: crlf` for it, so only the `text` half of the query saves it — a file outside any repo, an empty or missing `file_path`, a symlinked file (the target is converted and the link kept) and a link whose target is outside any repo (left untouched). As a supplementary check on the *installed* copy, `/reload-plugins` and trigger `Write|Edit|MultiEdit` inside a repo that declares an `eol`; do any binary check on a **copy** of an addon repo, never a live one, and compare with `cmp`.

## Conventions & hot zones (footguns)

### Plugin-wide

- **Adding/removing a command or agent is a six-touch change.** Keep these in sync or the docs drift:
  1. the `commands/*.md` or `agents/*.md` file (with the Step 0 block; a new shared command also goes into `SHARED` in `scripts/check_overlays.py`, or its Step 0 goes unchecked),
  2. its overlay `profiles/wow/<name>.md`, if it is shared and has WoW deltas,
  3. the README table (Shared / WoW-only / Subagents),
  4. **both** manifest descriptions (`plugin.json` + `marketplace.json`),
  5. the version in `plugin.json` (bump it),
  6. `docs/ARCHITECTURE.md` — the Module Map's command list and counts, and the `commands/*.md` row's file count in `## Documentation map`.
- **Naming:** shared commands keep plain names; WoW-only ones carry the `wow-` prefix. Never add a WoW-only behavior to a shared base — it goes in the overlay, so a generic run cannot load it.
- **Command wrappers for subagents** (`review`, `wow-standards-audit`) get a one-line row in their Commands table that points at **Subagents**, where the real description lives — follow that taxonomy for any future wrapper.
- **All `/wow-addon:` names are retired.** `/wow-addon:<x>` → `/dev-copilot:<x>` for the 14 shared commands and `/dev-copilot:wow-<x>` for the eight WoW-only ones; agent `wow-addon:review` → `dev-copilot:review`, `wow-addon:standards-audit` → `dev-copilot:wow-standards-audit`. The only intentional live mentions of `wow-addon` are: the README migration note, frozen dated bundles, the "successor to" / "formerly" provenance notes (manifests, `.dev-copilot`, the audit specs' rotation table), the tests that assert the retired state dir and repo stay unrecognized, and this file's history. A grep for `wow-addon:` / `/wow-addon` should find nothing else.
- **Commit style:** terse capitalized imperative subjects, no Conventional-Commits prefix (dev-copilot's pre-merge history used `feat:`; the merged repo follows wow-addon's style); work lands on a feature branch (`feat/<date>-<topic>`) merged into `master` with `--no-ff`, then the branch is deleted; commits carry a `Co-Authored-By: Claude …` trailer (match the recent `git log`).

### WoW specs and overlays

These bind the `wow-*` commands, the WoW overlays, and `agent-review.md`; command names below are the post-merge ones.

- **Runtime-fetch specs** (`wow-standards-audit`, `wow-new-addon`, `wow-revendor-standards`, `wow-automated-tests` — which fetches the `AUTOMATED_TESTS.md` playbook alongside the standard's index — `wow-perf-analysis`, which fetches `PERF_ANALYSIS.md` the same way, and, for its guardrail only, the WoW review): fetch the playbook + standard with `curl -fsSL` (verbatim); WebFetch is a **lossy fallback only** — its summarizer mangles verbatim content. If the standard can't be resolved: `wow-standards-audit`/`wow-new-addon`/`wow-revendor-standards` must **hard-stop** (their whole output is worthless without it), but `review` must **degrade gracefully** — it fetches the standard only to keep its own remediation compliant, so on failure it proceeds with the review and notes that the standards cross-check was skipped. Don't "fix" `review` to hard-stop.
- **Hard-code only the entry points; discover the rest by following links.** The standard is **split** — `standards/STANDARDS.md` is an index whose **Sections** list links one file per section under `standards/standards/`. Specs fetch `STANDARDS.md` and then **every section file it lists**; they **must not** hard-code section filenames, so the standard can be re-organized upstream without touching this plugin. The only fixed remote paths are the playbooks (`AUDIT.md`/`NEW_ADDON.md`/`AUTOMATED_TESTS.md`/`PERF_ANALYSIS.md`), `standards/STANDARDS.md`, and `standards/NEW_ADDON_CONTEXT.md` (fetched verbatim at scaffold time and read from a scratch path — **never** written into an addon repo; a stored `docs/agent-context.md` is anti-pattern #49).
- **A Ka0s addon's root is three docs plus `LICENSE`** — the full `README.md`, the **stub** `CLAUDE.md`, and `DEPENDENCIES.md` (the toolchain contract: every dependency with the evidence for it, split runtime / development / release-and-assets, WSL2-Ubuntu install commands that actually work, one-line verification per tool). **Its `docs/` is the canonical trio** — `ARCHITECTURE.md`, `testing.md`, `smoke-tests.md` — **plus five verification-and-record docs** (the generated `test-cases.md`, `performance.md`, `perf-analysis/README.md`, `automated-tests/README.md`, and the generated `automated-tests/RESULTS.md`) — four of those five are unconditional, and `perf-analysis/README.md` is required **only while the perf harness is wired**, so an addon holding the `performance-§12` no-combat-path exemption ships four of them and no `docs/perf-analysis/` at all — **plus the six unconditional Tier 1 topic-detail docs** (`scope.md`, `module-map.md`, `schema.md`, `settings-panel.md`, `data-flow.md`, `common-tasks.md`), with **Tier 2** (`slash-dispatch.md`, `midnight-quirks.md`, `compat-layer.md`, `message-bus.md`, `profiles.md`, `debug.md`) required per its stated trigger and otherwise recorded as a *Not applicable* row in `ARCHITECTURE.md`'s `## Documentation map`, and **Tier 3** addon-specific and free-form (documentation-§3). **`## Documentation map` has four tables, not three** — Required, Conditional, **Verification and record** and Addon-specific: the seven docs that belong to no tier (`testing.md`, `smoke-tests.md` and the five record docs) had no table until the standard named the fourth, and every addon then in the roster had written it themselves; `perf-analysis/README.md` is the one of the seven that registers in Conditional instead, against its Tier 2 trigger, and whether `ARCHITECTURE.md` registers itself is a **MAY** no spec may file either way. There is **no** `docs/complexity.md` (retired in standard v2.19.0), **no** `docs/file-index.md` or `docs/conventions.md` (retired v2.23.0), and **no** `docs/agent-context.md`; the root `CLAUDE.md` stub is the only agent brief in the repo. **Never state any of these counts without naming its members** — an unfilled slot is what makes a spec reconstruct a deleted file from memory. (This repo is `kind=tooling` and is *not* bound by the addon doc set: `documentation-§8` gives a documentation-and-tooling repo the **reduced hub** instead, a `docs/ARCHITECTURE.md` with five sections (Overview, Module Map read as the file-and-path map, Known Limitations, `## Documentation map`, `## Documented deviations`) beside the root `CLAUDE.md`, `DEPENDENCIES.md` and contributor-facing `README.md`. Its root `CLAUDE.md` is a full brief by design.)
- **Automated test records are recorded, and only two of the four suites gate a commit.** The vendored `tests/_kit/run-automated-tests.sh` runs lint, the headless harness, the offline perf scenarios and `lizard` (over the kit's sighted shadow from kit revision 35, with a function-count parity check whose mismatch count is `suites.complexity.blindFiles`, and with `-L 1500` so its function-length threshold is the layout-§1 file cap and `suites.complexity.warnings` counts functions above CCN 15 and nothing else), writing a frozen bundle per run to `docs/automated-tests/<YYYYMMDD-HHMMSS>/` plus a row in `RESULTS.md` — **one** file overwritten in place so git history is the trend line. **`lint` and `tests` gate the run and the commit; `perf` and `complexity` never fail a run and never gate a commit** — a threshold that fails a run teaches everyone to reach for `--no-verify`. The **tag** is a different checkpoint: it is gated on **all four** suites at `pass` plus **zero** functions above **CCN 15** and **zero** blind files, evaluated by `/dev-copilot:bump-version` (its WoW overlay) from the run's `manifest.json` (`automated-tests-§3`, *The release gate*; see *Two checkpoints, two different gates* below). A missing tool is a **skip recorded with its reason**, never a pass. A full bundle is produced at **release**, before the tag, and never gates a commit. `docs/complexity.md` was retired in standard v2.19.0.
- **Two recording commands, two harnesses, and the line between them is load-bearing.** `/dev-copilot:wow-automated-tests` **runs** four out-of-game suites and records what they produced; it owns `docs/automated-tests/`. `/dev-copilot:wow-perf-analysis` **cannot run anything** — the measurement happened in a live client on the player's machine, and it reaches this session only as a paste (the printed report plus the one-line JSON dump); it owns `docs/perf-analysis/<YYYYMMDD-HHMMSS>/`. The failure that separation prevents: an agent handed half a paste, or none, filling the gap from the offline `tests/perf.lua` scenarios — an offline `bytes/iter` cited as in-game evidence conflates two harnesses the standard deliberately keeps apart, and the resulting bundle reads as measured when nothing measured it. No report and no dump means **ask and stop**, never a bundle. Neither command may write into the other's tree.
- **A complexity number in Lua is not read the way it is elsewhere, and a disposition expires.** `lizard` counts every `and`/`or` short-circuit as a decision, so a run of `t.k = rec.k or D.k` defaulting lines scores CCN 13 with no visible branching — a high number usually means dense **defaulting/guarding**, not tangled control flow, and the fix is a module-level data table plus one loop rather than restructured logic. Any spec that writes a watch-list disposition must treat **Accepted** as having a shelf life: carried across three consecutive release runs, the entry is owed a fix or a tracked deviation ID (anti-pattern #53). And a refactor triggered by the report is itself constrained (`performance-§11`) — no body dumped into a nameless helper (#52), no dispatch table built inside the function it serves, no behavior change in a mechanical diff, and a characterization test **before** refactoring anything untested.
- **Two checkpoints, two different gates.** **Commits** are gated on lint + the headless harness only (`testing-§4`), and `perf`/`complexity` never fail a run — that rule is retained verbatim, and the vendored runner's exit code **MUST NOT** be changed to implement any threshold, because the same script is the commit gate. **Releases** are gated on all four suites plus **zero functions above CCN 15** with **`blindFiles` at 0** (a manifest from a kit before revision 35 has no such field and is NOT EVALUATED), evaluated by `/dev-copilot:bump-version` reading the run's `manifest.json` **before it edits anything** (`automated-tests-§3`, *The release gate*). A `skip` is not a pass: an unmeasured suite blocks the release as NOT EVALUATED. The asymmetry is the point — a commit gate is routed around with `--no-verify`; a release has no such hatch.
- **`docs/complexity.md` is retired (standard v2.19.0).** The raw report is each bundle's `complexity.txt`; the trend line and watch list are `docs/automated-tests/RESULTS.md`. No spec may scaffold, regenerate or sync a `docs/complexity.md` — finding one in an addon is a **pre-adoption finding to report**, never a doc to keep current.
- **`review` measures before it reviews, and only what runs outside the game.** Generically its Step 0b re-runs the repo's own detected lint/tests/type-check. In a WoW repo (`agent-review.md`) it re-runs `luacheck`, the headless suite, a fresh `--list` inventory, `tests/perf.lua`, the runner's sighted complexity suite (`--suite complexity --no-bundle`, never raw `lizard`), any `Makefile` `test` target, the vendored-copy `diff`, and the four-class **cross-addon pass** — because a committed artifact is a claim about a *past* state of the code, and the review is about the present one. The cross-addon pass is the one step that reads *outside* the addon under review: the collection's stated deployment is all eleven loaded at once, and a collision between two addons that are each correct alone is invisible to every per-addon suite, since each repo tests its own copy and both stay green. Two invariants hold it up and both are easy to break by simplifying it. Every census is scoped to the **TOC-derived load list**, not `grep -r` over the repo — a `RegisterChatCommand` sweep through `libs/` reports a token from a vendored Ace3 comment, and a raw-`SLASH_*` sweep that keeps PrettyChat's tracked-but-unloaded `GlobalStrings/` captures reports well over a thousand violations where the loaded source has none. And the clean result is **written down as a baseline table** so the next pass diffs against it instead of re-deriving it; a recorded non-finding is what makes it cheap enough to actually get run. Two boundaries hold it in place: **fresh output goes to scratch, never into the repo** (the inventory moves with the change that moves the pass count; the complexity report moves at release), and **anything needing a login is not run** — it is written up in `03_SMOKE_TESTS.md` for a human. A missing tool is a **stated skip**, never an inferred pass and never a silent fallback to the committed artifact. This is measurement in service of findings, not a gate: `run-tests` still owns running suites as a gate and offering to fix them, and `review` reports a red suite rather than fixing it mid-review.
- **Reference the standard's sections as `filename-§N`.** A whole section is its bare filename (`architecture`, `anti-patterns`); a subsection is `filename-§N` (`architecture-§5`, `documentation-§1`), the number being that section's **local** count. The old global `§N.M` notation is retired — don't use or reintroduce it in specs or artifacts.
- **Artifact directories in the target repo, and the one store that isn't a file.** Three specs write dated bundles into the repo they operate on, and each owns its own tree: `review` → `docs/reviews/<date>/` in a WoW repo (`reviews/<date>/` generically), `wow-standards-audit` → `docs/audits/<date>/`, `wow-revendor-libka0s` → `docs/revendor/<date>-v<tag>/` (plus a two-tag `<date>-v<first>-v<last>/` consolidated span bundle when vendored tags went unrecorded). All are **frozen history** — `issue-audit` reads their execution plans to find unexecuted rows but must never edit them. The pending store is **not a file**: `docs/pending/LEDGER.md` is **retired** and its store is **GitHub issues on the repo itself**, so no spec may create, recreate or mirror that ledger. Every issue carries exactly **two labels** that are the data: one `state:` label and one `severity:` label. Other labels may ride alongside without being data: the `bug`/`enhancement` tag `issue-add` applies, and `source:curseforge`, which `wow-curseforge-comments` adds to record where an issue came from. Neither is a state or a severity, and no command reads one as either. (The label model is generic and lives in the shared `issue-*` bases; the WoW overlays add the collection scope and the bundle sweeps.)

  **Status** — `state:done` (green `00ff00`, closed) and `state:will-not-do` (blue `0000ff`, closed) are **terminal**, dropped entirely on later runs; `state:triaged` (yellow `ffff00`, open) is a decided "not now", collapsed to a count; `state:untriaged` (red `ff0000`, open) means nobody has been asked, so it must never read as agreement.

  **Severity** — `severity:critical` (red `110000`), `severity:high` (orange `110800`), `severity:medium` (yellow `111100`), `severity:low` (green `001100`), against the ladder `issue-audit` defines. It is not decoration: it is the **queue order** `issue-triage` interviews in and a reporting dimension in both read commands, so a wrong severity puts an item in front of or behind the wrong things.

  Matching is on the item ID + **evidence hash** in the issue body, so an item only re-opens if its evidence changes. **The labels are the data, and the title carries neither.** Two conventions preceded them and both are retired: the `marker + word` ledger-table affordance (`🟢 done`), and the `[<Status>] <Title>` **title prefix**. Never reintroduce either, never write a severity word into a title, never add a fifth value to either set or rename one, and never keep a second copy of either in the body — the body records the severity *rationale*, not the level. A leftover `[status]` prefix on an old issue is stale text: **the label wins**, and the prefix is stripped by the write commands as part of the stray repair. **Every issue always carries both labels**, so there is no unlabeled state: an issue that arrives without a `state:` label (web UI, or someone not using these commands) is **repaired on sight** to `state:untriaged`, and the repair is **always announced**, including by the two read commands, because a listing command that mutates silently is worse than one that doesn't repair at all. A missing `severity:` label is repaired only by the commands that read bodies (`issue-audit`, `issue-triage`); the read commands show it as `—` and say how many, because a severity guessed from a title alone lands in a grid people then reason from. Any spec that creates the labels does so with `gh label create --force`, which is idempotent and repairs a drifted color on the way.
- **Discovery and triage are separate commands, and the separation is load-bearing.** `issue-audit` sweeps and files `state:untriaged` with a severity; it **never interviews and never changes code**. `issue-triage` interviews and records; it **changes the issue store only**. Neither writes code. A sweep is mechanical and safe to run over every repo at once; a triage costs a human decision per item — fusing them gated the cheap half behind the expensive one. Consequences a spec must respect: triage **records rather than implements**, so accepting an item produces a `state:triaged` issue carrying the approach, not a code change; an early stop leaves the remainder `state:untriaged` and **untouched**, so silence is never a decision and nothing is published that the user never saw; and `gh` is **load-bearing** — without it neither command can run and both must stop rather than degrade. Every decision recorded is **public**, which `issue-triage` must say up front rather than let the user discover from a notification.
- **All issue work goes through the `gh` CLI subcommands** — `gh issue list`, `gh issue create`, `gh issue edit`, `gh issue close`, `gh issue comment`, `gh issue view`, with `--json` where structured data is needed. **Never `gh api graphql`**, and never a hand-rolled GraphQL query against `api.github.com/graphql`: reaching for GraphQL first is a real, observed failure that burns a round trip on a deprecated path before falling back. `gh api repos/{owner}/{repo}/issues` is the only acceptable REST fallback. Because status and severity live in **labels**, listing by either is a plain **`--label` query** over `gh issue list --json number,title,state,labels` — not a title filter, not `--search`, not GraphQL. The label-writing subcommands `gh label list` and `gh label create --force` are in-surface for the specs that ensure the eight labels exist. This binds `issue-audit`, `issue-add`, `issue-fetch-all`, `issue-summary`, `issue-details`, `issue-triage`, `wow-harvest-standards`, `wow-revendor-libka0s`, `wow-curseforge-comments` and the `wow-standards-audit` agent alike.
- **Vendored folders in the target addon are read-only, and every spec that can edit code must say so.** Ka0s addons vendor a shared library at `libs/LibKa0s/` (whole-folder, TOC-listed as its own aggregate `.xml`) and a shared headless test kit at `tests/_kit/` — a *sibling* of the library's ship folder, never under `libs/`. Both are copies. A defect in either is an **upstream** finding: fix it in the library repo, bump the file's LibStub minor, re-vendor the whole folder as its own commit in every consumer. A local patch is reverted silently by the next copy, and the behavior comes back as a regression with **no cause in the consumer's history** — which is why the WoW review reports these as `[upstream]` and `run-tests` (its WoW overlay) refuses to patch under them even to turn a suite green. **One spec writes into both, and only one way:** `wow-revendor-libka0s` replaces them **wholesale from a tag of the library repo**, never file by file — per-module copying is how cross-major skew gets manufactured — and it is bound by the same `[upstream]` rule everywhere else, including inside its own adoption step. The one deletion it may make inside `libs/` is a file the diff reports as `Only in <Addon>/libs/LibKa0s`, i.e. removed upstream and left behind by `cp -r`, which adds and overwrites but never deletes. The corollary for `wow-new-addon`: the shared subsystems (chat printer, debug console, options toolkit, slash dispatcher, perf harness, test framework) are **consumed, not written** — one setup file per adopted module, holding a **descriptor** plus a **degradation stub**, and nothing else. Don't let any spec drift back toward hand-building or local patching; anything genuinely missing goes upstream as an **additive** field.
- **The `LibKa0s` provenance line lives in the addon's root `CLAUDE.md`, not its `README.md`.** `Bundles [LibKa0s](https://github.com/tusharsaxena/LibKa0s) vX.Y.Z (MIT).` names the tag both vendored payloads (`libs/LibKa0s/` and `tests/_kit/`) were copied from, and it is the **input** to the consumer-side vendored-payload gate the addon runs as `tests/test_vendor_sync.lua` (`testing-§11`). It moved out of `README.md` at **LibKa0s v1.8.1 / test-kit revision 9**, and the gate has **no fallback**: a line left in the README reads to it as no line at all, and a **missing** line fails the case rather than skipping it (unlike an absent sibling checkout, which does skip). Four consequences bind specs here: `wow-new-addon` writes the line into the `CLAUDE.md` stub it scaffolds; `sync-docs` **moves** one it finds in a README rather than refreshing it in place; `bump-version` must **never** roll that `vX.Y.Z` to the addon's new version — it is the library's tag, not the addon's; and `wow-standards-audit` reads it to pick the tag it diffs the vendored copies against, instead of the sibling repo's `HEAD`. The line only moves on a re-vendor, in the **same commit** as the bytes, in both directions.
- **The addon README carries no bundled-library inventory, and its standard badge is not a link** (`documentation-§1`, anti-patterns #58/#59). No `## Libraries` / `## Bundled libraries` / `## Libraries and credits` / `## Credits and libraries` / `## Credits and bundled libraries` section, and no library roll-call smuggled into the intro paragraph — the Ace3/LibSharedMedia/LibDataBroker/LibDBIcon list, the "everything ships inside it, nothing else to install" prose and the `Bundles [LibKa0s] …` sentence all stay out, because a vendored-library list is a contributor fact with two homes that are actually read (`DEPENDENCIES.md`, `docs/ARCHITECTURE.md`) and the README is written for players. What survives is genuinely **external** credit only — a third-party artist, a font, a sound pack — as an optional `## Credits` section placed **last**, after `## Version History`; with nothing external to credit, the section does not exist. The standard badge is the bare `![Standard](https://img.shields.io/badge/Ka0s-WoW_Addon_Standard-yellow)` (`_`, not `%20`) and **MUST NOT** be re-wrapped in `[…](https://github.com/tusharsaxena/WowAddonStandards)` — the binding standards reference is the TOC `## X-Standard:` field and `CLAUDE.md`'s `## Standards compliance (read first)`; the badge declares, it does not navigate. No spec may scaffold, restore or "tidy up" either shape back into an addon.
- **The audit rotation is three kinds of repository, and one repo is deliberately outside it.** The eleven addons in `WowAddonStandards/standards/ADDONS.md` are measured against the whole standard; `LibKa0s` against `library-stack-§7`'s applicability list; and `WowAddonStandards` and `dev-copilot` (via its `.dev-copilot` `kind=tooling`) against the **documentation lane** — same eight steps, same five artifacts, same `docs/audits/<date>/`, but the four checks are internal consistency between rules, cross-references that resolve, worked examples against the trees they cite, and inventories against the trees they count, graded on how far a defect reproduces rather than on who can reach it (in a repo that ships nothing to a client, the addon grading rule flattens every finding to Low and sorts nothing). Those two entered the rotation late because they are docs-only, and that is exactly what made them expensive: they hold `AUDIT.md` and the review agent, so a defect in either was reproduced across twenty passes and reviewed by none. **`Ka0sAddonsCommonTasks` is not in the rotation and must not be added** (it detects as `wow/tooling` only so cross-repo runs started there keep the collection scope) — a README and a tree of frozen planning bundles, no Lua, no TOC, no `libs/`, no suites, nothing a checklist binds to, and an audit there would report the absence of an addon as a stack of MUST failures. The mechanical checks that have no subject in a documentation repo (lint, the headless runner, the vendored `diff -r`, the provenance line, `lizard`) are recorded **not applicable**, never *not run*.
- **The CurseForge journal is data, and data never lands in this plugin or an addon.** `wow-curseforge-releases` and `wow-curseforge-comments` write only to `Ka0sAddonsCommonTasks/journal/curseforge/` (or `$KA0S_CF_JOURNAL`), whose `README.md` is the schema, and `scripts/curseforge_journal.py` refuses a journal path inside this plugin or inside any roster addon. Keep test fixtures **synthetic**: a real comment pasted into `scripts/test_curseforge_journal.py` is journal data in the wrong repo. The comments come from the CurseForge site's own undocumented endpoint (`www.curseforge.com/api/v1/mods/<id>/comments`), which pages over replies as well as top-level comments and returns a reply detached from its parent when the parent fell on an earlier page; the fetcher walks every page, flattens and dedupes by id, and a shape change is reported as such, never papered over by scraping the page. Changelogs are stored as one `- subject (sha7)` line per commit: the packager's changelog is the full `git log` since the previous tag, bodies and all (5.6 MB of the first 5.7 MB run), and the bodies already live in each addon's history. A journal run commits straight to the journal repo's default branch, and pushes only with `push`.
- **`wow-standards-audit` is read-only** on the audited repository — it only writes under `docs/audits/<date>/`. Don't let it edit code.
- **Two cycles, one word.** The *standards* cycle is `wow-revendor-standards` down / `wow-harvest-standards` up, and it carries a **reference**: pointing at the standard, never copying its text into a repo (#49). The *library* cycle is `wow-revendor-libka0s` down, and it carries **bytes**: whole payloads copied from a tag of `LibKa0s` into `libs/LibKa0s/` and `tests/_kit/`. Same verb, different object, opposite rule about copying — don't let a spec generalize from one to the other. Three consequences bind here. The payload is taken from a **tag** via `git archive`, never the working tree, because the consumer's own `tests/test_vendor_sync.lua` resolves the tag its provenance line names and asserts the vendored bytes match the library **at that tag** — an untagged copy passes a local `diff` and then fails the addon's suite, which is how the untagged kit revision was caught upstream. The bytes and the `CLAUDE.md` provenance line move in **one commit**, because that gate fails a split. And `wow-revendor-libka0s` is the **only** spec that moves that `vX.Y.Z`: `bump-version` must never roll it, `sync-docs` migrates a stale line out of a README during a doc sweep, and `wow-revendor-libka0s` removes a README line only when it has just superseded it.
- **The standards cycle runs both ways, and the two halves must not blur.** `wow-revendor-standards` runs **in an addon repo** and carries the standard **down**; `wow-harvest-standards` runs **in the standards repo** and carries the collection's learnings **up**. The load-bearing asymmetry: `wow-harvest-standards` is **read-only on every addon repo and on `LibKa0s`** — not politeness, but what keeps its evidence independent of its argument. If it edited as it swept, the next run would read its own text back as if it were nine repos agreeing. For the same reason neither command ever edits a frozen `docs/audits/` or `docs/reviews/` bundle: those are the harvest's primary source, and their value is that they record what was true against the standard of *their* date. Cross-repo synthesis is `wow-harvest-standards`' whole reason to exist — every other WoW spec here reads exactly one repo — so a run that only re-reads one repo has done nothing new.
- **The ripple is the dangerous part of a standards change, not the rule.** A rule edited in its section and missed in the index blurb, the anti-pattern range, `NEW_ADDON_CONTEXT.md`, `EXECUTIVE_SUMMARY.md` or a playbook leaves the standard **contradicting itself**, and the stale copy is what gets followed. Upstream has already spent a whole patch release cleaning up one incomplete ripple — a count still reading "quartet" beside three named members, which an agent completed from memory with the very file that release had deleted. `wow-harvest-standards` owns that checklist and must discharge it item by item.
- **The quirks catalog is the one piece of upstream text that *is* vendored into an addon.** Everything else about the standard is pointed at, never copied (#49) — but client quirks are reference data, not instructions, and an addon needs them next to the code that works around them. So they get the `libs/LibKa0s/` discipline instead: a marked block, copied **whole**, replaced **wholesale**, never patched locally, and **stamped with its source version** (a vendored copy without its version cannot be told stale from current — the same reason LibStub minors exist; this is the deliberate exception to "no standard version in a repo file", which governs the *reference*). Below the end marker is the addon's own section: `wow-revendor-standards` must not touch it beyond pruning entries promoted upstream, because it is `wow-harvest-standards`' input and editing it would let one command launder its own text into the other's evidence.
- **Three specs touch the same doc set from different directions; keep the split.** `wow-standards-audit` measures the addon *against* the standard and writes a frozen bundle (read-only, findings). `sync-docs` reconciles docs against the repo's **own code** — count claims, slash parity, dead exports, the comment-citation check, doc scaffolding, and (WoW overlay) the migrate-then-delete flow for `docs/agent-context.md`. `wow-revendor-standards` reconciles docs against the **current upstream standard text** and edits in place — the three-place reference (`documentation-§6`), retired and unresolvable forms swept out of the **whole repo**, and gate claims the standard has since qualified. The boundary rule: anything needing code analysis is `sync-docs`'s, anything needing the fetched standard is `wow-revendor-standards`'. Two consequences that look like gaps and are not — `wow-revendor-standards` **flags** a missing `docs/` member or root `DEPENDENCIES.md` instead of creating it (an `ARCHITECTURE.md` written without reading the code, or a `DEPENDENCIES.md` written without the evidence, is worse than an absent one) and **reports** `docs/agent-context.md` instead of deleting it (two specs owning one destructive action is how the salvage half gets skipped). It also **must not** rewrite frozen `docs/audits/` or `docs/reviews/` bundles even when they use retired notation: they record what was true against the standard of *their* date, which is what a dated artifact is for. And "revendor" there means the **reference**, never a copy — storing the standard's text in an addon is the same failure as storing the context pack (#49).
- **Two specs may touch a comment, and their edit boundary is one boundary written twice.** `wow-revendor-standards`' 3b sweep corrects a citation of the **standard** sitting in a code or config comment; `sync-docs`' comment-citation check (now in the generic base, with Lua-specific scope and tokens in the WoW overlay) corrects a comment citing **this repo** — a path that is not there, a `:N` past the end of the file, a `Symbol.Member` with no definition and no call site, a version the tree does not stamp. That last kind is narrower than it sounds and deliberately so: it fires only where the repo holds something authoritative to check against (in an addon, the migration table's highest `to =` and the `CLAUDE.md` provenance line), so a version quoted in prose with no such authority stays prose. Both are a deliberate, narrow relaxation of "documentation only", and both are fenced on the same four sides: **that sweep/check only**, **comments only** (a string literal, a key or a value is reported, never edited), **explicit confirmation every time** (silence is a decline, not a default), and **never a guessed target** (the user names the replacement or the item stays flagged). The rule's purpose survives intact — an agent licensed to rewrite every repo's `CLAUDE.md` still cannot reach a line that runs. The two are written to match on purpose: **if they ever disagree, that is the bug**, and the fix is to bring them back into alignment rather than to let one drift wider. Widening what either command *reads* never widens what it may *write*, and neither may touch `libs/`, `Libs/` or `tests/_kit/` at all.
- **`finalize` is the only spec that pushes on its own.** Every other git-touching spec here stops at the commit unless it is explicitly told otherwise: `commit.md`'s hard rule is **never push unless the `push` flag was given**, the default being no push, and the flag is consumed only as the leading token so a message containing the word is never acted on. That rule stands; the finalizer overrides it deliberately — it pushes unasked, and says so in its own body — because the ordering it exists to enforce (a vendored library must be **on origin** before a consumer whose docs cite it lands) is not expressible if pushing is somebody else's later step. Don't "fix" the inconsistency by teaching the other specs to push.
- **`finalize` establishes its scope before it acts, and never guesses it.** It covers both the one-repo and the many-repo case, so the scope is a decision, not a given. It proceeds unasked only when the answer is certain — explicit `$ARGUMENTS` (including `here`), exactly one dirty repo, or several linked by *hard* evidence (this session touched each, a vendored folder matches a changed sibling source, a changed file cites a sibling path that also changed). Anything else — unrelated-looking candidates, repos the session never touched, unaccountable dirt — prints per-candidate changes and asks. Too narrow strands half a changeset unpushed while the other half references it on origin; too wide commits someone's work-in-progress under a message that is then wrong for both, which no revert fixes. Don't let it collapse back into "multi-repo only" or into silently picking the likely scope.
