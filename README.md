# dev-copilot

A Claude Code plugin for day-to-day development: git diff and commit helpers, documentation drift sync, a principal-engineer review, test and release helpers, a GitHub-issue workflow, and progress reporting. It works in any repository.

It is also the home of the World of Warcraft addon tooling that used to ship as the separate [`wow-addon`](https://github.com/tusharsaxena/wow-addon) plugin. Every command checks what kind of repository it is running in. In a WoW addon repo (or `LibKa0s`, `WowAddonStandards` or a tooling repo) it applies the full Ka0s WoW Addon Standard behavior; everywhere else it stays generic and never loads the WoW instructions. Its WoW specs are written against the Ka0s WoW Addon Standard v2.77.0; the commands that fetch the standard at runtime follow whichever version is current.

## Repo profiles

Each command starts by running `dev-copilot-profile`, a small detector the plugin puts on your `PATH`. It prints the repo's **profile** (`wow` or `generic`) and **kind**:

| Kind | Detected when | Profile |
|---|---|---|
| `standards` | the repo (directory or `origin`) is `WowAddonStandards` | wow |
| `tooling` | the repo is the `Ka0sAddonsCommonTasks` workspace, or opts in (this repo does) | wow |
| `library` | the repo is `LibKa0s`, or has a root `LibKa0s.toc` | wow |
| `addon` | a root `*.toc` has an `## Interface:` line | wow |
| `generic` | anything else | generic |

Shared commands carry their WoW behavior in an **overlay** (`profiles/wow/<command>.md`) that is read only when the profile is `wow`. WoW-only commands (`wow-*`) refuse to run in a generic repo, except `wow-new-addon`, which creates the repo it would otherwise classify.

**Override.** If detection gets a repo wrong, add a `.dev-copilot` file at its root:

```
profile=wow        # or: generic
kind=addon         # optional with profile=wow: addon | library | standards | tooling
```

## Commands

### Shared — every repo

| Command | What it does | Extra in a WoW repo |
|---|---|---|
| `/dev-copilot:diff` | Read-only summary of uncommitted changes: what changed, the likely intent, and the risks (dead exports, broken references, undeclared dependencies, lockfile drift, debug leftovers, suspicious untracked files). Never dumps the raw diff. | Events registered but never unregistered, libraries missing from the TOC, an `## Interface:` that needs a bump. |
| `/dev-copilot:commit [push] [ask\|<message>]` | Stage and commit with a generated message that matches the repo's style. `ask` confirms the message first; any other text is used verbatim. **Does not push unless `push` is the leading token.** Never amends, never force-pushes, never `git add -A`, and pauses on secret-looking or unusual files. | Lua/TOC-specific untracked-file checks. |
| `/dev-copilot:sync-docs` | Rewrite `README.md`, `CLAUDE*`/`AGENTS*.md`, `ARCHITECTURE*.md`, `TODO.md`, `DEPENDENCIES.md` (when present) and, conservatively, `CHANGELOG.md` to match the code. Verifies count claims, command/script parity, config and dependency drift, dead exports, and comments that cite paths, lines or symbols that do not exist (comment fixes only on confirmation). Shows a drift inventory before writing. | The Ka0s root doc set and `docs/` trio, slash/COMMANDS parity, the `LibKa0s` provenance line, no bundled-library inventory, README Version History instead of a changelog. |
| `/dev-copilot:review [path\|all\|branch]` | Runs the `review` subagent (below). | The WoW review. |
| `/dev-copilot:run-tests [suite\|path]` | Detect and run every lint, type-check and test suite the repo declares (npm/pnpm/yarn scripts, pytest/ruff/mypy, go, cargo, make, gradle/maven, dotnet, and more), report a combined pass/fail table, and offer to fix failures. | `luacheck`, the headless `tests/` harness and any Makefile `test` target, all through the bounded runner. |
| `/dev-copilot:bump-version [X.Y.Z] [commit] [tag] [push]` | Bump the version everywhere it appears and roll the history since the last tag into `CHANGELOG.md`. Refuses to bump unless the test battery passes. Never commits, tags or pushes unless you pass `commit`, `tag` or `push`. | TOC version, README Version History (addons) vs `CHANGELOG.md` (library repos), and the four-suite release gate with zero functions above CCN 15 plus the release automated-test bundle. |
| `/dev-copilot:finalize [repos\|here]` | Finish a changeset: sync docs, commit, merge the feature branch into the default branch, push, delete the branch. Works on one repo or several, establishes the scope from evidence and asks when unsure. The only command that pushes on its own. | Collection dependency order (`LibKa0s` and the standard before their consumers), vendored folders as evidence. |
| `/dev-copilot:execution-status [plan-path] [brief]` | One-screen status of the work planned in this conversation: done, running, left, percent complete and a time to finish. Reads a plan ledger when one exists and reconciles it with git and live background work. Read-only. | — |
| `/dev-copilot:issue-audit [here\|all\|<repo>] [scope]` | Discovery: sweep TODO/FIXME/stub markers, doc open questions, an `Unreleased` changelog section, stashes, follow-up commits, review bundles and unacted Claude memory, and file anything new as a GitHub issue labeled `state:untriaged` plus a `severity:`. Never interviews, never changes code. | Also sweeps the newest `docs/audits/` and `docs/reviews/` execution plans (revendor bundles are not swept; their declines are already issues). Collection labels and severity ladder; `all` = the Ka0s roster from `ADDONS.md`, upstreams included, with the Lua sweep on addon rows only. |
| `/dev-copilot:issue-triage [here\|all\|<repo>]` | Decision: walk every `state:untriaged` issue, most severe first, and record your call as `state:triaged` (not now), `state:will-not-do` or `state:done`. Changes the issue store only. | The collection's severity ladder and resolutions; `all` = the Ka0s roster from `ADDONS.md`, upstreams included. |
| `/dev-copilot:issue-add [seed text]` | File one well-formed issue with `state:` and `severity:` labels, shown for approval first. | The collection's severity ladder; environment facts from the TOC. |
| `/dev-copilot:issue-fetch-all [filter]` | List the repo's issues, filterable by status, severity, any label, or `closed`/`all`. Read-only. | The collection's severity ladder. |
| `/dev-copilot:issue-details [here\|all\|<repo>] [states] [severities]` | Issues grouped by status, most severe first, one line each. Defaults to the live store (untriaged + triaged). | `all` = the Ka0s roster from `ADDONS.md`, upstreams included. |
| `/dev-copilot:issue-summary [here\|all\|<repo>]` | Counts only: status × repo, severity × repo over open issues, and status × severity, with a short read of what they imply. Defaults to the current repo. | Defaults to the whole Ka0s collection: the roster from `ADDONS.md`, upstreams included. |

`all` in the issue commands means the repos you name, or else the sibling git checkouts next to this one (you confirm the list before anything is written). In a WoW repo it means the Ka0s collection instead, and means it identically in all four commands that take it (`issue-audit`, `issue-triage`, `issue-details`, `issue-summary`): every row of `WowAddonStandards/standards/ADDONS.md`, which is the addon table plus its library table (`LibKa0s`) and its documentation-and-tooling table (`WowAddonStandards` and this plugin), each repo tagged with its kind. In `issue-audit` and `issue-triage` the upstream rows get the generic sweep, and the addon-only checks, such as the Lua marker sweep, run on addon rows only. All issue work goes through the `gh` CLI.

### WoW-only — WoW addon, `LibKa0s`, `WowAddonStandards` and tooling repos

Five commands read the living Ka0s WoW Addon Standard at [tusharsaxena/WowAddonStandards](https://github.com/tusharsaxena/WowAddonStandards): `/dev-copilot:wow-new-addon`, `/dev-copilot:wow-standards-audit`, `/dev-copilot:wow-revendor-standards`, `/dev-copilot:wow-automated-tests` and `/dev-copilot:wow-perf-analysis`. They fetch that repo's `NEW_ADDON.md` / `AUDIT.md` / `AUTOMATED_TESTS.md` / `PERF_ANALYSIS.md` playbooks and `standards/` docs at runtime and follow them, so they always track the current standard. All five need network access to that public repo when they run. `/dev-copilot:wow-harvest-standards` goes the other way. It runs inside the standards repo, reads the whole collection and promotes what it has learned into the standard.

`/dev-copilot:wow-revendor-libka0s` is the same cycle for the shared library rather than the standard, and it works from local disk instead of the network. It reads the sibling [`LibKa0s`](https://github.com/tusharsaxena/LibKa0s) checkout beside the addon and takes its payload from that repo's newest tag. The tag matters. Every consumer's `tests/test_vendor_sync.lua` resolves the tag named in its `CLAUDE.md` provenance line and asserts that the vendored bytes match the library at that tag, so a copy taken from an untagged working tree passes a local `diff` and then fails the addon's own suite. The command needs the checkout present, not network access, and it needs `gh` only to file the declines it records.

`/dev-copilot:wow-curseforge-releases` and `/dev-copilot:wow-curseforge-comments` keep a journal of the addons' CurseForge pages. The journal lives in the sibling `Ka0sAddonsCommonTasks/journal/curseforge` (or `$KA0S_CF_JOURNAL`), never in an addon repo or this plugin. Both need network access and a CurseForge Core API key from console.curseforge.com, set as `CURSEFORGE_API_KEY` in the environment or in `~/.claude/dev-copilot/curseforge.env`. The comments command also needs `gh` to file the issues you accept.

| `/dev-copilot:wow-new-addon <AddonName> [description]` | Scaffold a new addon born compliant with the Ka0s WoW Addon Standard. The command fetches the `NEW_ADDON.md` playbook and context pack and follows them. You get an Ace3 skeleton, the modular layout and MIT; the root doc set (the full `README.md`, the `CLAUDE.md` stub, and `DEPENDENCIES.md`, which is the evidence-based toolchain contract); the canonical `docs/` trio (`ARCHITECTURE.md`, `testing.md`, `smoke-tests.md`); the five verification-and-record docs (`test-cases.md`, `performance.md`, `perf-analysis/README.md`, `automated-tests/README.md`, `automated-tests/RESULTS.md`); and the six unconditional Tier 1 topic-detail docs (`scope.md`, `module-map.md`, `schema.md`, `settings-panel.md`, `data-flow.md`, `common-tasks.md`). `smoke-tests.md` follows the shape every addon in the collection uses: an index of themes, checks with stable IDs like `SLASH-3`, and a `## Non-English client` section whose `LOC-1` check is written from the new addon's own locale-sensitive code. Every Tier 2 trigger is evaluated and answered in `ARCHITECTURE.md`'s `## Documentation map`, and the first automated-test bundle is written before the `v0.1.0` tag. `automated-tests/README.md` and the gate table in `docs/testing.md` state both checkpoints from the fetched `automated-tests-§3`: lint and tests gate the commit, and the tag is gated on all four suites plus zero functions above CCN 15. The vendored runner's exec bit is set in the git index (`git update-index --chmod=+x`), because `core.fileMode=false` on a DrvFs mount makes a bare `chmod` invisible to git. The context pack itself is read at runtime and never written into the addon (`documentation-§3`). The diagnostics dump is wired from the start: `modules/Diagnostics.lua`, a `diagnostics` row in the slash dispatcher, and the fixed `## Reporting a bug` section in the README (`debug-logging-§14`). The README it writes carries the unlinked standard badge, no bundled-library inventory and no numbered list (`documentation-§1`). The `LibKa0s` provenance line, `Bundles [LibKa0s](…) vX.Y.Z (MIT).`, names the tag both payloads were vendored from. It goes into the root `CLAUDE.md` stub, where the vendored-payload gate reads it. The shared subsystems (chat printer, debug console, options toolkit, slash dispatcher, perf harness, test harness) are consumed from the vendored `LibKa0s` library and its test kit, one setup file per adopted module, instead of being hand-built. |
| `/dev-copilot:wow-bump-interface [number]` | Update `## Interface:` in the current addon's TOC(s) to the current Retail (Live Servers) value. It works on this repo only and does not recurse. Pass the number, or leave it out to use the current Live value; the command asks you to confirm if it is unsure. |
| `/dev-copilot:wow-revendor-standards [repos]` | Refresh the addon's in-repo reference to the Ka0s WoW Addon Standard so its documentation matches the standard as it exists today. That reference lives in three places (`documentation-§6`): the TOC `## X-Standard:` field, the README standard badge and `CLAUDE.md → ## Standards compliance (read first)`. The badge is the bare `![Standard](…)` image. `documentation-§1` makes it a declaration and not a link, so a badge found wrapped in a link is unwrapped rather than left or restored. The command also sweeps retired and unresolvable forms out of the whole repo, not just `docs/`: the global `§N.M` notation (rewritten to `filename-§N`), section filenames renamed upstream, a `filename-§N` whose number is past that section's real range, a root- or `docs/`-set count stated without naming its members, and the retired "drop-in" label for the scaffolding pack. It looks for gate claims the standard has since qualified, too. A "perf and complexity never fail a run" sentence that names no checkpoint, in `docs/testing.md`, `docs/automated-tests/README.md` or the root `CLAUDE.md`, is rewritten from `automated-tests-§3` so every gate statement names both commit and release. The sweep skips `libs/`, `tests/_kit/` and the frozen `docs/audits/`, `docs/reviews/` and `docs/automated-tests/` bundles, and the `RESULTS.md` lead-in is reported as runner-generated rather than edited. The command fetches `standards/STANDARDS.md` and every section file its Sections list links (never a hard-coded filename), hard-stops if it can't, and prints a drift inventory before writing anything. Mechanical items apply automatically. Anything that overwrites the repo's own prose asks first, and so does every item in a multi-repo run. It defaults to the repo at cwd and never widens on its own; pass repos or `all` to sweep siblings. It also vendors the standard's quirks catalog into the addon's `docs/` quirks file as a marked block. That block is copied whole, replaced wholesale, never patched locally and stamped with its source version, under the same discipline as `libs/LibKa0s/`. The addon's own quirks section is left alone, because it is `/dev-copilot:wow-harvest-standards`' input, apart from pruning entries that have since been promoted upstream. This is documentation work with one narrow exception. A standards citation in a code or config comment is reported with `file:line` and corrected only on your explicit confirmation, comment-only. `/dev-copilot:sync-docs` has the same edit boundary for repo-internal citations, and the two are identical on purpose. Otherwise the command never edits code, never writes the standard's rules into the repo, never creates missing `docs/` members or a missing root `DEPENDENCIES.md`, never hand-edits the generated `test-cases.md` / `automated-tests/RESULTS.md`, and never edits frozen `docs/audits/` or `docs/reviews/` bundles. It reports `docs/agent-context.md` instead of deleting it, since `/dev-copilot:sync-docs` owns that migration. It differs from `wow-standards-audit`, which measures and writes a frozen bundle, and from `sync-docs`, which reconciles docs against code. |
| `/dev-copilot:wow-revendor-libka0s [repos] [--tag vX.Y.Z]` | Carry the current LibKa0s into the addon and decide what to do with what arrived. This is the consumer-side counterpart to the library's release-side re-vendor checklist. It is also the only command that moves the `Bundles [LibKa0s] vX.Y.Z (MIT)` provenance line in `CLAUDE.md`. `/dev-copilot:bump-version` must never roll that line, because it holds the library's tag, not the addon's. The command reads the sibling `../LibKa0s` checkout and takes the payload from its newest tag via `git archive`, never from the working tree, because the consumer's own `tests/test_vendor_sync.lua` resolves the tag the provenance line names and asserts that both payloads match the library at it. The delta comes first. It covers the claimed version against the actual LibStub minors; the per-file minor table, read from the tag's `LibKa0s.xml` rather than a hard-coded list; both diffs, content and bytes, where content-clean but bytes-dirty means a line-ending divergence to renormalize and never an edit to `libs/`; the kit-revision pairing rule (v1.9.0+ requires kit revision 11 in the same commit); which majors the addon actually consumes; and the contract delta. The contract delta is the one class of change that no number and no byte can show: a surface keeps its name and its arguments but changes when it is called, or what it requires back from a member the host supplied. To find it, the command diffs the tag's `docs/api/<Major>/version-<minors>-docs.md` against the document for the version the addon is on. It chains the documents by each header's `Superseded by` row instead of guessing filenames, reads the diff for whatever is not `Since`-marked, and binds the result to the addon's own `__Attach*` sites. What it finds there is an adoption blocker, never a candidate. The interview never offers one. It is fixed in the copy commit, or the run stops before the copy, because a payload carrying one passes `luacheck`, the harness and `test_vendor_sync.lua` and is wrong only on screen. Next the command copies both payloads whole, `libs/LibKa0s/` and `tests/_kit/`, and never a single module, since per-module copying is how cross-major skew gets manufactured. It rolls the provenance line, gates on `luacheck` and the headless harness, and commits the bytes and the line together, because the consumer's gate fails a split. Then it works out which new surfaces are candidates. What arrived for free needs no decision. What needs a host change, or a whole unadopted module, does. Each candidate carries `file:line` evidence from the `Since` markers in the library's own `docs/api/<Major>/version-*-docs.md` and from its `CHANGELOG.md` blocks, never from memory. It also carries the addon's own recorded reason for any past decline, so a structural refusal is not re-litigated every release. You are interviewed one candidate at a time, most valuable first, and told up front that a decline is filed as a public GitHub issue (`state:triaged` or `state:will-not-do`, plus a severity). Stop early and the rest stay undecided and untouched. Accepted candidates are implemented with a characterization test first, whose assertion proves that the same bytes render rather than that the code still runs; then `luacheck` and the harness go green, with one commit per candidate. `libs/`, `Libs/` and `tests/_kit/` stay read-only apart from the wholesale copy, so a defect in either payload is an `[upstream]` finding and never a local patch. The delta base comes from the addon's `CLAUDE.md` provenance line, never from the library's previous tag. The command writes a frozen bundle to `docs/revendor/<date>-v<tag>/` (01_DELTA, 02_CANDIDATES, 03_DECISIONS, 04_EXECUTION_PLAN, 05_SUMMARY). When tags the addon vendored went unrecorded, it adds one consolidated span bundle, `docs/revendor/<date>-v<first>-v<last>/`, holding only 01_DELTA and 05_SUMMARY. It defaults to the repo at cwd. Pass repo names or `all` to sweep every sibling holding a `libs/LibKa0s/`; they are processed one after another. **It never pushes.** |
| `/dev-copilot:wow-harvest-standards [scope]` | The upstream half of the cycle. It harvests what the whole collection has learned and promotes it into the Ka0s WoW Addon Standard. Run it inside the `WowAddonStandards` repo; it is read-only on every addon repo. It sweeps ten categories: convergent patterns (≥3 repos with the standard silent, so codify them) and divergent ones (N solutions, which become a rule or a `LibKa0s` extraction candidate); anti-patterns; Midnight quirks; the `docs/audits/` + `docs/reviews/` corpus; standard-internal contradictions an audit had to punt to the user; closed `state:will-not-do` issues across the collection, which are accepted deviations the standard never heard about, read with `gh issue list --label "state:will-not-do"` and never GraphQL; rules nobody satisfies (and rules nobody cites); `LibKa0s`↔standard drift; undocumented emergent conventions; and tooling gaps whose fix is a lint rule rather than prose. Findings are filtered three ways before anything is proposed. They are checked against the standard version each bundle was measured under, so settled history isn't re-proposed, and against `open-evolutions.md`, where a known item counts as a vote rather than a duplicate. They also have to clear an evidence bar of ≥2 repos, or 1 repo plus a stated cost. The command writes a frozen `harvests/<YYYY-MM-DD>/` bundle and interviews you per proposal (accept / defer / reject). Accepted proposals are applied with the full ripple: section file, Sections blurb, anti-pattern range, changelog entry, a version bump classified as patch/minor/major, `NEW_ADDON_CONTEXT.md` + pack version, `EXECUTIVE_SUMMARY.md`, and the `AUDIT.md`/`NEW_ADDON.md` playbooks. It closes by naming the rollout debt per repo. It never auto-resolves an ambiguous signal, and it never commits or pushes. |
| `/dev-copilot:wow-automated-tests` | Run and record the full four-suite battery through the vendored runner: lint, headless tests, offline perf scenarios and `lizard` complexity. It writes a frozen bundle to `docs/automated-tests/<YYYYMMDD-HHMMSS>/`, rolls the run into `RESULTS.md` and writes the `ANALYSIS.md`. `lint` and `tests` gate the commit. `perf` and `complexity` are recorded but never fail a run or block a commit. The release tag is a different matter: it is gated on all four suites passing plus zero functions above CCN 15, measured sighted with `blindFiles` at 0 (`automated-tests-§3`). The command fetches the living `AUTOMATED_TESTS.md` playbook. |
| `/dev-copilot:wow-perf-analysis [paste]` | Record and interpret an in-game perf run. This is the counterpart to `/dev-copilot:wow-automated-tests`, and the one recording command that cannot run anything it records. The measurement happened in a live client, in combat, on the player's machine, so the report and the JSON dump are mandatory inputs that come from the player. After the run they paste the output of `/<slash> perf report` and `/<slash> perf dump`; one copied debug-log buffer is fine, and the command splits it. If the paste is missing, the command asks for it and stops. It never invents, completes or reconstructs a capture. Nor does it fill a gap from the offline perf scenarios, which answer a different question and belong to the automated-test bundle that produced them (`automated-tests-§7`). Given the paste, it splits the report from the dump and keeps the lifecycle lines as the capture's provenance. Then it validates the record against the repo: `addon`, `version` against the TOC, `schema` against the vendored lib, the report's figures reconciled against the dump's `%.4f`, and both arms with `frames > 0`. A mismatch is reported, not corrected. The bundle stamp comes from the record's own `timestamp` in local time, so it says when the capture happened rather than when it was written up. The frozen `docs/perf-analysis/<YYYYMMDD-HHMMSS>/` holds exactly three files: `report.md` (the printed report plus the run's lifecycle log lines), `dump.json` (the record verbatim, on one line, never pretty-printed or re-ordered) and `ANALYSIS.md` (the write-up). After that the command rewrites the store's standing `README.md` and its index table of captures. The write-up rules that matter: never fabricate a figure. Read the buckets rather than `deltaMsPerFrame`, because below roughly 0.5 ms/frame the delta is unresolved, and unresolved is not the same fact as zero. Treat a negative delta as evidence that the environment moved between arms, and say what the arms did not hold constant. An addon with no `core/PerfSetup.lua` has not wired the harness. One holding a recorded `performance-§12` no-combat-path exemption ships no store at all. Both cases get stated, not scaffolded around. The command fetches the living `PERF_ANALYSIS.md` playbook. |

## Subagents

| Agent | When to invoke |
|---|---|
| `review` (`/dev-copilot:review`) | A principal-engineer review, scoped by argument: no argument reviews the current changes (working tree, or branch vs. base when clean), a path reviews that subtree, `all` the whole repo, `branch` the branch vs. its base. It **measures first**, running the repo's own lint and tests so findings rest on today's numbers, then covers design and structure, correctness, error handling, security, concurrency, performance, API and dependency hygiene, tests, naming and dead code. Writes `01_FINDINGS.md` … `05_FINAL_SUMMARY.md` under `reviews/<YYYY-MM-DD>/` and prints a summary. **In a WoW repo** it becomes the WoW review: every out-of-game suite re-run (`luacheck`, the headless harness and its inventory, `tests/perf.lua`, the sighted complexity suite, vendored-copy sync, the cross-addon pass), the WoW-specific checks (taint and combat lockdown, events, frames, deprecated APIs, localization, AceConfig), a guardrail against the living standard, and a bundle under `docs/reviews/<YYYY-MM-DD>/` with `03_SMOKE_TESTS.md`. |
| `wow-standards-audit` (`/dev-copilot:wow-standards-audit`) | A read-only compliance audit against the Ka0s WoW Addon Standard. It fetches the living `AUDIT.md` playbook and `standards/STANDARDS.md` (the standard's index) at runtime, follows the index's Sections list to fetch every section file, and measures the repository section by section and against the `anti-patterns` list. The result is a frozen `docs/audits/<YYYY-MM-DD>/` bundle: current state, deviations with stable IDs, evidence, remediation design and an execution plan. Before anything else it settles which rule set binds the repository, because the rotation holds three kinds of repo, not one. Every addon in the standard's roster (`standards/ADDONS.md`) takes the whole standard. `LibKa0s` takes `library-stack-§7`'s applicability list. The two documentation-and-tooling repos, `WowAddonStandards` and `dev-copilot`, take the documentation lane. That lane has the same steps and the same artifacts, but it measures internal consistency between rules, cross-references that resolve, worked examples against the trees they cite, and inventories against the trees they count, and it grades on how far a defect reproduces rather than on who can reach it. Those two repos hold `AUDIT.md` and `agents/review.md`, the documents every other pass runs on. A defect in either was reproduced across twenty passes and reviewed by none until they entered the rotation. `Ka0sAddonsCommonTasks` is deliberately left out, since it is frozen planning bundles with nothing for a checklist to bind to. Deviations are graded by impact, not rule strength. High is reserved for what a user, their SavedVariables or their session can hit today, so a doc-only MUST failure is Low or Info and still names its MUST. Where several observations follow from a single unadopted subsystem, the audit files one root with `derived from <ID>` dependents and reports both the roots-only headline tally and the total. Before filing any MUST as open, it reads the recorded-deviation register: `docs/ARCHITECTURE.md` § Documented deviations, the repo's issue-audit GitHub issue store (read via `gh issue list` and keyed on the `state:` label), the root `CLAUDE.md` and `docs/scope.md`. A ratified row makes the gap a recorded deviation outside the MUST tally. A decline recorded only as a closed `state:will-not-do` issue, with no register row, is itself a `documentation-§3` deviation to file. It re-reads and quotes every `file:line` it cites before writing, reconciles figures across artifacts, and states each count's exact command and scope. The mechanical checks are run, not reasoned about. They are lint, the headless suite, a `diff -r` of every vendored Ka0s-owned library against its sibling source repo, and the complexity run, through the vendored runner's sighted suite. The `diff -r` uses the tag the addon's root `CLAUDE.md` provenance line names, not the sibling's `HEAD`: diffing against `HEAD` measures scheduling rather than compliance, and that drift is invisible to both repos' test suites. The provenance line's own placement is audited too. It has lived in `CLAUDE.md` and not `README.md` since LibKa0s v1.8.1 / test-kit revision 9, and a missing line is a failing gate rather than a skip. The complexity run is compared against the addon's latest automated-test bundle (`docs/automated-tests/<run>/complexity.txt`) and the `RESULTS.md` watch list, and the audit records the drift and how stale that run is by its stamp. An absent tool or sibling repo means the check is not run. It is reported that way, never inferred. The audit never modifies addon code. Run it with `/dev-copilot:wow-standards-audit`. |

## Hooks

- The line-ending hook normalizes files on Write, Edit and MultiEdit. When a file is written or edited inside a git repo, the plugin asks git what that file's `.gitattributes` declares and normalizes to it: CRLF in a client-bound Ka0s repo (the addons and `LibKa0s`), LF in one that ships nothing to the WoW client (the standards repo and this one). Every Ka0s repo declares one or the other (`line-endings`). The hook asks for `text` as well as `eol`, so a file marked `binary` is left alone even though the pin still answers `eol: crlf` for it (`line-endings-§7`). It is silent on files with no declared `eol` as well, and it never blocks a write. It lives at `hooks/hooks.json` + `scripts/normalize-eol.sh`.
- The bounded-runs hook keeps heavy runs on Bash in check. It is a `PreToolUse` hook that refuses an unbounded `lua tests/run.lua` / `lua tests/perf.lua`, `run-automated-tests.sh`, `luacheck` or `lizard`, and names the bounded runner to prefix instead: `~/.claude/dev-copilot/bin/ka0s-bounded <command>`. That path is a symlink the hook keeps pointed at the installed `scripts/ka0s-bounded`. The plugin also ships `bin/ka0s-bounded`, a POSIX `sh` wrapper that `exec`s the runner, and Claude Code puts the plugin's `bin/` on PATH, so the bare `ka0s-bounded <command>` works too. The runner caps process memory (`ulimit -v`, `KA0S_KIT_PROC_MB`, default 2048), the process tree's memory and task count (a `systemd-run --user --scope`, `KA0S_KIT_TREE_MB` default half of RAM, `KA0S_KIT_TASKS` 256) and wall-clock time (`KA0S_KIT_TIMEOUT_S`, 900; off a terminal a timeout stops the whole process group, children included, and on a terminal `--foreground` keeps Ctrl-C working). It queues on a machine-wide `flock` slot pool (`~/.cache/ka0s-kit/slots`, `max(1, MemAvailable×0.6 / KA0S_KIT_SLOT_MB)` slots, `KA0S_KIT_SLOT_MB` default 2048, recomputed while it waits so a run queued under memory pressure takes a freed slot, or exactly `KA0S_KIT_SLOTS`), so several repos' suites can run in parallel without exhausting memory. `KA0S_KIT_CGROUP=off` skips the tree cap, and `KA0S_KIT_GUARD=off` drops every bound (for a debugger, never for a gate). Exit codes pass through, and 124 (timeout) and 137 (killed) get a one-line explanation. Only a command in command position counts. The same words inside quotes or a heredoc body, such as a commit message or an `ANALYSIS.md` written with `cat <<'EOF'`, are prose and pass. Lua runs in a repo whose `tests/_kit` is LibKa0s kit revision 23+ are let through, because that kit bounds itself with the same variables. The hook exists because an unbounded runaway suite once OOM-killed a whole WSL2 VM and the session driving it. To opt out for one command, add an inline `KA0S_BOUNDED_HOOK=off` assignment.

## Migrating from wow-addon

The `wow-addon` plugin is retired; everything it did lives here.

1. `/plugin uninstall wow-addon` (both plugins installed together would run every hook twice).
2. Install or update dev-copilot (below).
3. Rename as you type: `/wow-addon:<x>` becomes `/dev-copilot:<x>` for `diff`, `commit`, `sync-docs`, `review`, `run-tests`, `bump-version`, `finalize`, `execution-status` and the `issue-*` commands, and `/dev-copilot:wow-<x>` for `new-addon`, `bump-interface`, `automated-tests`, `perf-analysis`, `revendor-libka0s`, `revendor-standards`, `harvest-standards` and `standards-audit`.

Plugin state moved from `~/.claude/wow-addon/` to `~/.claude/dev-copilot/`, and the bounded runner's stable path is now `~/.claude/dev-copilot/bin/ka0s-bounded`. Nothing reads the old folder: finish any interrupted `issue-triage` run with wow-addon before switching, then delete `~/.claude/wow-addon/`.
