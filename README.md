# wow-addon

A Claude Code plugin for World of Warcraft addon development.

It scaffolds new addons that are born compliant with the Ka0s WoW Addon Standard, audits an addon against that standard, refreshes an addon's in-repo reference to it as it evolves, and harvests the collection's learnings back into it. It bumps an addon's interface version to match Live Servers, syncs documentation against the actual code and releases new versions. On the testing side, it runs the addon's test battery, records the full four-suite battery into frozen dated bundles, and records and interprets an in-game perf run into frozen `docs/perf-analysis/<run>/` bundles. It also finalizes a changeset across one repo or several, triages everything still pending across an addon's code, docs, issues and prior audit plans, manages its GitHub issues, and reviews changes for WoW-specific correctness: taint, deprecated APIs, frame leaks, missing localization, AceConfig misuse and dead code.

Five commands read the living Ka0s WoW Addon Standard at [tusharsaxena/WowAddonStandards](https://github.com/tusharsaxena/WowAddonStandards): `/wow-addon:new-addon`, `/wow-addon:standards-audit`, `/wow-addon:revendor-standards`, `/wow-addon:automated-tests` and `/wow-addon:perf-analysis`. They fetch that repo's `NEW_ADDON.md` / `AUDIT.md` / `AUTOMATED_TESTS.md` / `PERF_ANALYSIS.md` playbooks and `standards/` docs at runtime and follow them, so they always track the current standard. All five need network access to that public repo when they run. `/wow-addon:harvest-standards` goes the other way. It runs inside the standards repo, reads the whole collection and promotes what it has learned into the standard.

`/wow-addon:revendor-libka0s` is the same cycle for the shared library rather than the standard, and it works from local disk instead of the network. It reads the sibling [`LibKa0s`](https://github.com/tusharsaxena/LibKa0s) checkout beside the addon and takes its payload from that repo's newest tag. The tag matters. Every consumer's `tests/test_vendor_sync.lua` resolves the tag named in its `CLAUDE.md` provenance line and asserts that the vendored bytes match the library at that tag, so a copy taken from an untagged working tree passes a local `diff` and then fails the addon's own suite. The command needs the checkout present, not network access, and it needs `gh` only to file the declines it records.

## Components

### Commands

| Command | What it does |
|---|---|
| `/wow-addon:new-addon <Name>` | Scaffold a new addon born compliant with the Ka0s WoW Addon Standard. The command fetches the `NEW_ADDON.md` playbook and context pack and follows them. You get an Ace3 skeleton, the modular layout and MIT; the root doc set (the full `README.md`, the `CLAUDE.md` stub, and `DEPENDENCIES.md`, which is the evidence-based toolchain contract); the canonical `docs/` trio (`ARCHITECTURE.md`, `testing.md`, `smoke-tests.md`); the five verification-and-record docs (`test-cases.md`, `performance.md`, `perf-analysis/README.md`, `automated-tests/README.md`, `automated-tests/RESULTS.md`); and the six unconditional Tier 1 topic-detail docs (`scope.md`, `module-map.md`, `schema.md`, `settings-panel.md`, `data-flow.md`, `common-tasks.md`). `smoke-tests.md` follows the shape every addon in the collection uses: an index of themes, checks with stable IDs like `SLASH-3`, and a `## Non-English client` section whose `LOC-1` check is written from the new addon's own locale-sensitive code. Every Tier 2 trigger is evaluated and answered in `ARCHITECTURE.md`'s `## Documentation map`, and the first automated-test bundle is written before the `v0.1.0` tag. `automated-tests/README.md` and the gate table in `docs/testing.md` state both checkpoints from the fetched `automated-tests-§3`: lint and tests gate the commit, and the tag is gated on all four suites plus zero functions above CCN 15. The vendored runner's exec bit is set in the git index (`git update-index --chmod=+x`), because `core.fileMode=false` on a DrvFs mount makes a bare `chmod` invisible to git. The context pack itself is read at runtime and never written into the addon (`documentation-§3`). The README it writes carries the unlinked standard badge, no bundled-library inventory and no numbered list (`documentation-§1`). The `LibKa0s` provenance line, `Bundles [LibKa0s](…) vX.Y.Z (MIT).`, names the tag both payloads were vendored from. It goes into the root `CLAUDE.md` stub, where the vendored-payload gate reads it. The shared subsystems (chat printer, debug console, options toolkit, slash dispatcher, perf harness, test harness) are consumed from the vendored `LibKa0s` library and its test kit, one setup file per adopted module, instead of being hand-built. |
| `/wow-addon:bump-interface [number]` | Update `## Interface:` in the current addon's TOC(s) to the current Retail (Live Servers) value. It works on this repo only and does not recurse. Pass the number, or leave it out to use the current Live value; the command asks you to confirm if it is unsure. |
| `/wow-addon:sync-docs` | Deep-analyze the addon and rewrite `README.md` / `CLAUDE*.md` / `DEPENDENCIES.md` / `ARCHITECTURE*.md` to eliminate drift. The analysis covers count verification, COMMANDS↔README slash parity, dead-export detection and toolchain-vs-`DEPENDENCIES.md` drift, where every entry has to be backed by evidence and nothing is speculative. There is also a comment-citation check over the addon's own source and config. It catches a comment naming a path that is not there, a `:N` past the end of the file, a `Symbol.Member` with no definition and no call site, a version the tree does not stamp, a migration step past the migration table's highest `to =`, and a vendored-library tag the `CLAUDE.md` provenance line does not carry. Each one is reported with `file:line` and corrected only on confirmation, comment-only, and never to a guessed target. `libs/`, `Libs/` and `tests/_kit/` are excluded as vendored payload. The command also scaffolds ARCHITECTURE.md and DEPENDENCIES.md. It enforces three README shape rules from `documentation-§1`. First, no bundled-library inventory: any `## Libraries` / `## Bundled libraries` / `## Libraries and credits` / `## Credits and libraries` heading comes out, as does the same roll-call smuggled into the intro prose, and only genuinely external credit survives, as a `## Credits` section placed last. Second, the standard badge stays the bare unlinked image. Third, the README carries no numbered list, because CurseForge does not render one: each `1.` list becomes `- ` bullets, with only the markers changed. If the `LibKa0s` provenance line (`Bundles [LibKa0s](…) vX.Y.Z (MIT).`) is still in the README, it gets moved to the root `CLAUDE.md`, since that is where the vendored-payload gate reads it (LibKa0s v1.8.1 / test-kit revision 9, no fallback). The generated docs (`test-cases.md`, `automated-tests/RESULTS.md`) are left alone: it reports their staleness rather than editing their numbers. A surviving `docs/complexity.md` (retired in standard v2.19.0) is reported, not synced. |
| `/wow-addon:revendor-standards [repos]` | Refresh the addon's in-repo reference to the Ka0s WoW Addon Standard so its documentation matches the standard as it exists today. That reference lives in three places (`documentation-§6`): the TOC `## X-Standard:` field, the README standard badge and `CLAUDE.md → ## Standards compliance (read first)`. The badge is the bare `![Standard](…)` image. `documentation-§1` makes it a declaration and not a link, so a badge found wrapped in a link is unwrapped rather than left or restored. The command also sweeps retired and unresolvable forms out of the whole repo, not just `docs/`: the global `§N.M` notation (rewritten to `filename-§N`), section filenames renamed upstream, a `filename-§N` whose number is past that section's real range, a root- or `docs/`-set count stated without naming its members, and the retired "drop-in" label for the scaffolding pack. It looks for gate claims the standard has since qualified, too. A "perf and complexity never fail a run" sentence that names no checkpoint, in `docs/testing.md`, `docs/automated-tests/README.md` or the root `CLAUDE.md`, is rewritten from `automated-tests-§3` so every gate statement names both commit and release. The sweep skips `libs/`, `tests/_kit/` and the frozen `docs/audits/`, `docs/reviews/` and `docs/automated-tests/` bundles, and the `RESULTS.md` lead-in is reported as runner-generated rather than edited. The command fetches `standards/STANDARDS.md` and every section file its Sections list links (never a hard-coded filename), hard-stops if it can't, and prints a drift inventory before writing anything. Mechanical items apply automatically. Anything that overwrites the repo's own prose asks first, and so does every item in a multi-repo run. It defaults to the repo at cwd and never widens on its own; pass repos or `all` to sweep siblings. It also vendors the standard's quirks catalogue into the addon's `docs/` quirks file as a marked block. That block is copied whole, replaced wholesale, never patched locally and stamped with its source version, under the same discipline as `libs/LibKa0s/`. The addon's own quirks section is left alone, because it is `/wow-addon:harvest-standards`' input, apart from pruning entries that have since been promoted upstream. This is documentation work with one narrow exception. A standards citation in a code or config comment is reported with `file:line` and corrected only on your explicit confirmation, comment-only. `/wow-addon:sync-docs` has the same edit boundary for repo-internal citations, and the two are identical on purpose. Otherwise the command never edits code, never writes the standard's rules into the repo, never creates missing `docs/` members or a missing root `DEPENDENCIES.md`, never hand-edits the generated `test-cases.md` / `automated-tests/RESULTS.md`, and never edits frozen `docs/audits/` or `docs/reviews/` bundles. It reports `docs/agent-context.md` instead of deleting it, since `/wow-addon:sync-docs` owns that migration. It differs from `standards-audit`, which measures and writes a frozen bundle, and from `sync-docs`, which reconciles docs against code. |
| `/wow-addon:revendor-libka0s [repos] [--tag vX.Y.Z]` | Carry the current LibKa0s into the addon and decide what to do with what arrived. This is the consumer-side counterpart to the library's release-side re-vendor checklist. It is also the only command that moves the `Bundles [LibKa0s] vX.Y.Z (MIT)` provenance line in `CLAUDE.md`. `/wow-addon:bump-version` must never roll that line, because it holds the library's tag, not the addon's. The command reads the sibling `../LibKa0s` checkout and takes the payload from its newest tag via `git archive`, never from the working tree, because the consumer's own `tests/test_vendor_sync.lua` resolves the tag the provenance line names and asserts that both payloads match the library at it. The delta comes first. It covers the claimed version against the actual LibStub minors; the per-file minor table, read from the tag's `LibKa0s.xml` rather than a hard-coded list; both diffs, content and bytes, where content-clean but bytes-dirty means a line-ending divergence to renormalize and never an edit to `libs/`; the kit-revision pairing rule (v1.9.0+ requires kit revision 11 in the same commit); which majors the addon actually consumes; and the contract delta. The contract delta is the one class of change that no number and no byte can show: a surface keeps its name and its arguments but changes when it is called, or what it requires back from a member the host supplied. To find it, the command diffs the tag's `docs/api/<Major>/version-<minors>-docs.md` against the document for the version the addon is on. It chains the documents by each header's `Superseded by` row instead of guessing filenames, reads the diff for whatever is not `Since`-marked, and binds the result to the addon's own `__Attach*` sites. What it finds there is an adoption blocker, never a candidate. The interview never offers one. It is fixed in the copy commit, or the run stops before the copy, because a payload carrying one passes `luacheck`, the harness and `test_vendor_sync.lua` and is wrong only on screen. Next the command copies both payloads whole, `libs/LibKa0s/` and `tests/_kit/`, and never a single module, since per-module copying is how cross-major skew gets manufactured. It rolls the provenance line, gates on `luacheck` and the headless harness, and commits the bytes and the line together, because the consumer's gate fails a split. Then it works out which new surfaces are candidates. What arrived for free needs no decision. What needs a host change, or a whole unadopted module, does. Each candidate carries `file:line` evidence from the `Since` markers in the library's own `docs/api/<Major>/version-*-docs.md` and from its `CHANGELOG.md` blocks, never from memory. It also carries the addon's own recorded reason for any past decline, so a structural refusal is not re-litigated every release. You are interviewed one candidate at a time, most valuable first, and told up front that a decline is filed as a public GitHub issue (`state:triaged` or `state:will-not-do`, plus a severity). Stop early and the rest stay undecided and untouched. Accepted candidates are implemented with a characterization test first, whose assertion proves that the same bytes render rather than that the code still runs; then `luacheck` and the harness go green, with one commit per candidate. `libs/`, `Libs/` and `tests/_kit/` stay read-only apart from the wholesale copy, so a defect in either payload is an `[upstream]` finding and never a local patch. The delta base comes from the addon's `CLAUDE.md` provenance line, never from the library's previous tag. The command writes a frozen bundle to `docs/revendor/<date>-v<tag>/` (01_DELTA, 02_CANDIDATES, 03_DECISIONS, 04_EXECUTION_PLAN, 05_SUMMARY). When tags the addon vendored went unrecorded, it adds one consolidated span bundle, `docs/revendor/<date>-v<first>-v<last>/`, holding only 01_DELTA and 05_SUMMARY. It defaults to the repo at cwd. Pass repo names or `all` to sweep every sibling holding a `libs/LibKa0s/`; they are processed one after another. **It never pushes.** |
| `/wow-addon:harvest-standards [scope]` | The upstream half of the cycle. It harvests what the whole collection has learned and promotes it into the Ka0s WoW Addon Standard. Run it inside the `WowAddonStandards` repo; it is read-only on every addon repo. It sweeps ten categories: convergent patterns (≥3 repos with the standard silent, so codify them) and divergent ones (N solutions, which become a rule or a `LibKa0s` extraction candidate); anti-patterns; Midnight quirks; the `docs/audits/` + `docs/reviews/` corpus; standard-internal contradictions an audit had to punt to the user; closed `state:will-not-do` issues across the collection, which are accepted deviations the standard never heard about, read with `gh issue list --label "state:will-not-do"` and never GraphQL; rules nobody satisfies (and rules nobody cites); `LibKa0s`↔standard drift; undocumented emergent conventions; and tooling gaps whose fix is a lint rule rather than prose. Findings are filtered three ways before anything is proposed. They are checked against the standard version each bundle was measured under, so settled history isn't re-proposed, and against `open-evolutions.md`, where a known item counts as a vote rather than a duplicate. They also have to clear an evidence bar of ≥2 repos, or 1 repo plus a stated cost. The command writes a frozen `harvests/<YYYY-MM-DD>/` bundle and interviews you per proposal (accept / defer / reject). Accepted proposals are applied with the full ripple: section file, Sections blurb, anti-pattern range, changelog entry, a version bump classified as patch/minor/major, `NEW_ADDON_CONTEXT.md` + pack version, `EXECUTIVE_SUMMARY.md`, and the `AUDIT.md`/`NEW_ADDON.md` playbooks. It closes by naming the rollout debt per repo. It never auto-resolves an ambiguous signal, and it never commits or pushes. |
| `/wow-addon:bump-version [X.Y.Z]` | Bump the addon's version everywhere it appears (TOC, code, README badges, Version History table, `CLAUDE*.md`) and roll the release history for everything since the last git tag into its proper home. `CHANGELOG.md` is a library file, not an addon file (`documentation-§1`). In an addon repo, the history's one mandated home is the README's "Version History" table. An existing root (or `docs/`) `CHANGELOG.md` is left byte-for-byte alone and reported as a violation to fold forward and delete, and one is never created. In a Ka0s-owned library repo, meaning one with no root `.toc`, the root `CHANGELOG.md` is required and gets the full entry. The command gates the release. Before any file is edited, it runs the full four-suite battery through the vendored runner, and it refuses to bump anything unless that run's `manifest.json` shows lint, tests, perf and complexity all passing with zero functions above CCN 15, measured sighted: `blindFiles` is printed with the gate and must be 0, and a manifest from a kit older than revision 35 has no such field and reads as NOT EVALUATED. A skipped suite is not a pass. If `lizard` is absent or there is no Lua 5.1 interpreter, that suite is reported as NOT EVALUATED along with the install command, and the release stops exactly as it would on a failure. The one exception is `perf` skipped because the addon ships no `tests/perf.lua`. That passes, and it has to be stated in the release notes, not only in the chat report that scrolls away. Only on a passing gate does the command edit anything, write that bundle's `ANALYSIS.md`, and refresh the `RESULTS.md` watch-list disposition for anything that newly crossed a threshold. If you give no version, it proposes a bump. |
| `/wow-addon:automated-tests` | Run and record the full four-suite battery through the vendored runner: lint, headless tests, offline perf scenarios and `lizard` complexity. It writes a frozen bundle to `docs/automated-tests/<YYYYMMDD-HHMMSS>/`, rolls the run into `RESULTS.md` and writes the `ANALYSIS.md`. `lint` and `tests` gate the commit. `perf` and `complexity` are recorded but never fail a run or block a commit. The release tag is a different matter: it is gated on all four suites passing plus zero functions above CCN 15 (`automated-tests-§3`). The command fetches the living `AUTOMATED_TESTS.md` playbook. |
| `/wow-addon:perf-analysis [paste]` | Record and interpret an in-game perf run. This is the counterpart to `/wow-addon:automated-tests`, and the one recording command that cannot run anything it records. The measurement happened in a live client, in combat, on the player's machine, so the report and the JSON dump are mandatory inputs that come from the player. After the run they paste the output of `/<slash> perf report` and `/<slash> perf dump`; one copied debug-log buffer is fine, and the command splits it. If the paste is missing, the command asks for it and stops. It never invents, completes or reconstructs a capture. Nor does it fill a gap from the offline perf scenarios, which answer a different question and belong to the automated-test bundle that produced them (`automated-tests-§7`). Given the paste, it splits the report from the dump and keeps the lifecycle lines as the capture's provenance. Then it validates the record against the repo: `addon`, `version` against the TOC, `schema` against the vendored lib, the report's figures reconciled against the dump's `%.4f`, and both arms with `frames > 0`. A mismatch is reported, not corrected. The bundle stamp comes from the record's own `timestamp` in local time, so it says when the capture happened rather than when it was written up. The frozen `docs/perf-analysis/<YYYYMMDD-HHMMSS>/` holds exactly three files: `report.md` (the printed report plus the run's lifecycle log lines), `dump.json` (the record verbatim, on one line, never pretty-printed or re-ordered) and `ANALYSIS.md` (the write-up). After that the command rewrites the store's standing `README.md` and its index table of captures. The write-up rules that matter: never fabricate a figure. Read the buckets rather than `deltaMsPerFrame`, because below roughly 0.5 ms/frame the delta is unresolved, and unresolved is not the same fact as zero. Treat a negative delta as evidence that the environment moved between arms, and say what the arms did not hold constant. An addon with no `core/PerfSetup.lua` has not wired the harness. One holding a recorded `performance-§12` no-combat-path exemption ships no store at all. Both cases get stated, not scaffolded around. The command fetches the living `PERF_ANALYSIS.md` playbook. |
| `/wow-addon:diff` | Summarize all uncommitted git changes in the addon: what changed, the likely intent, and the risks. |
| `/wow-addon:commit [push] [ask\|<message>]` | Stage and commit changes with a generated commit message that matches the project's style. Pass `ask` to approve the message first, or a message to use verbatim. **By default it does not push; pass `push` to push the branch afterwards.** The flag is only recognized as the leading token, so a message containing the word "push" is never mangled or acted on. It never force-pushes and never pushes a commit that did not land. A rejected push is reported, not resolved by pulling or rebasing. |
| `/wow-addon:finalize [repos]` | Finish a changeset, in the current repo alone or across several sibling repos. The command settles the scope first and never guesses. It uses the repos you name (or `here`) if you pass them, and the single dirty repo if only one is dirty. It takes all of them when hard evidence proves they are one changeset. Otherwise it prints each candidate's changes and asks. With more than one repo in scope, it derives the dependency chain from evidence. A vendored shared library is finalized and pushed before the consumers that carry it, and a doc line citing `../<Repo>/…` is an edge like any other. Then, per repo, it runs `sync-docs`, that repo's own gate including the vendor-drift diff, and `commit`; merges any feature branch with `--no-ff`; pushes; and deletes the branch with `-d`. In a parallel multi-repo run, `sync-docs` is content only, since nobody is there to confirm each repo; in a single-repo run it asks as usual. Independent repos run in parallel, one agent per repo. A red gate, a merge conflict or a rejected push stops that repo alone, and the real output is reported. This is the one command that pushes without being asked. `/wow-addon:commit` pushes only when handed the `push` flag. |
| `/wow-addon:execution-status [plan-path] [brief]` | Show where the planned work stands, on one screen. You get what is done, what is running, what is left in order, a percent complete as "n of m" (coded-but-in-review work is counted separately) and a time to finish, given as a clock time with the arithmetic behind it. It works for a single multi-step task, where the plan comes from the conversation, and for long runs driven by subagents and dynamic workflows across several repos. The denominator is everything the conversation planned. That means a documented plan's status ledger or checkboxes (`docs/superpowers/plans/`, `_dev/PLAN*.md`, a `TODO.md`, or a path you pass), plus every request and promised step added after it. Each unit's status is reconciled against evidence: commits per repo, the working tree, and live background work read with non-blocking `TaskOutput`. Git wins when the ledger lags, and "done" needs a commit or an artifact. The time to finish comes from this effort's own measured pace, per track, with parallel tracks overlapped and the fixed tail added. When nothing has been measured yet, the report says so instead of guessing. `brief` cuts the report down to the headline, the phase table and the next three steps. The command is read-only. It never ticks a ledger, commits, restarts work, waits on a running task or messages a running agent, because a message can wake a duplicate of a workflow's subagent. |
| `/wow-addon:run-tests` | Run the addon's entire test battery. It auto-detects and runs luacheck lint, the headless Lua `tests/` harness and any Makefile `test` target, reports a combined pass/fail summary, and offers to diagnose and fix failures. Non-gating measurement runners such as `tests/perf.lua` are skipped on purpose: they measure rather than verify, and their scenarios are not test cases. The `lizard` complexity report is out of scope for the same reason, and a stronger one. Its checkpoint is release, and gating commits on it is what teaches a collection to reach for `--no-verify`. The vendored `tests/_kit/` harness counts as harness, not a suite. A kit-sync (vendor-drift) failure is reported separately, since the fix is a re-vendor rather than an edit. |
| `/wow-addon:issue-audit [here\|all\|<repo>] [scope]` | The discovery half of the issue pair. It sweeps the addon for everything still hanging: TODO/FIXME/stub markers, unexecuted items from the newest audit and review execution plans, doc open questions and Known Limitations, an `Unreleased` CHANGELOG section, stashes and follow-up commits, and recorded-but-unacted Claude memory. Each item is reconciled against the issue store by evidence hash. After showing you the list, it files anything genuinely new as an open issue labelled `state:untriaged` plus a `severity:` label. It never interviews you and never changes code, and that is why it is cheap enough to run often and across every repo at once. Items already tracked are counted, not re-filed, and terminal ones are dropped. If the repo lacks the eight collection labels (`state:*`, `severity:*`), the command creates them. It also repairs any issue that arrived without a status or severity label, and strips a leftover legacy `[status]` title prefix on the way. It defaults to the repo at the cwd; pass `all` or a repo name. Narrow further with `code`, `docs`, `issues`, `memory`, or a path. It requires `gh`, because the store is remote. |
| `/wow-addon:issue-triage [here\|all\|<repo>]` | The decision half of the issue pair. It takes every open `state:untriaged` issue, most severe first by its `severity:` label, and puts each one to you in turn with its verbatim evidence and location. Each comes with 2–3 concrete resolutions specific to that item, plus **Keep it open — real work, not now** and a permanent **Will not do**. Your call is recorded by swapping the `state:` label in a single `gh issue edit` and appending a rationale comment. `state:will-not-do` and `state:done` are closed; `state:triaged` stays open. If you dispute a severity, the issue is re-labelled on the spot and the queue re-orders. The command is decision-only and changes the issue store and nothing else. Agreeing that something should be done records the approach on a `state:triaged` issue; it does not write the code. Stopping early leaves the rest `state:untriaged` and untouched, so silence is never recorded as a decision. It defaults to the repo at the cwd. |
| `/wow-addon:issue-fetch-all [filter]` | List the GitHub issues on the addon's repo (via `gh issue list`). Filter by status label (`untriaged`, `triaged`, `done`, `will-not-do`), by severity (`critical`, `high`, `medium`, `low`) or by any other label, or pass `closed`/`all`. Status and severity filters combine, since both are plain `--label` queries. The report is sorted most severe first and shows status, severity, state, labels, author and age, with the URLs below it and status/severity tallies above. It is read-only: a missing label is reported here, never repaired. |
| `/wow-addon:issue-add` | Create a well-formed GitHub issue (via `gh issue create`). It gathers a title, a tag (bug/enhancement), a severity and the details, and fuzzy input is fine. The severity is proposed with a justification you can overrule. The issue gets a plain title with no status prefix and carries `state:untriaged` (or `state:triaged` when you are explicitly filing something already postponed), the `severity:` label and the tag. You see it for approval before it is created. The command makes sure the eight collection labels exist first. |
| `/wow-addon:issue-summary [all\|here\|<repo>]` | How much, how bad, and where, in counts only. It prints three cuts. There is a status × repo grid (`done` / `will-not-do` / `triaged` / `untriaged`) and a severity × repo grid over open issues only, because closed severities say nothing about what to do next. The third is a status × severity crosstab, and its `untriaged × critical` cell is the first thing worth reading. After the grids comes a short read of what the numbers imply, grounded in the grids and nothing else: concentration, whether volume and severity point at different repos, and how much of the backlog is unsized. It defaults to the whole collection; pass `here` or a repo name. It never lists issues. The only write is adding a missing `state:` label, which it always announces. It never assigns a severity, since that needs the body read. |
| `/wow-addon:issue-details [here\|all\|<repo>] [states] [severities]` | What, item by item. Issues are grouped by status into sub-sections, and each is listed with its severity, title, a one-line description drawn from the body, age and URL, most severe first within each block. A per-repo severity tally sits under the repo heading. By default it shows the live store, `state:untriaged` and `state:triaged`. The terminal states are history, and printing them by default buries the ones that need you. Pass `done`, `will-not-do`, `closed` or `all` to widen it, or a severity to narrow it. Status is a heading rather than a column because the row-width budget is a correctness constraint and severity earns the space more. It never invents a description: an issue whose body has nothing usable gets `—`. Apart from the same announced status-label repair, it is read-only. |

### Subagents

| Agent | When to invoke |
|---|---|
| `review` | A focused review of WoW-specific issues: taint and combat lockdown (including secret-value leakage), event over-registration, frame leaks, deprecated APIs, missing localization, AceConfig/Settings UI misuse, NBSP/tooltip-pattern bugs, dead exports, and project-internal convention drift (COMMANDS dispatcher parity, single-write-path bypass), which applies only when the addon has those conventions. It measures before it reviews. Every suite that works outside the game client is re-run: `luacheck`, the headless `tests/` harness plus a fresh `--list` inventory, the offline `tests/perf.lua` scenarios, the vendored runner's sighted complexity suite (`--suite complexity --no-bundle`, never raw `lizard`, which is blind in Lua) to a scratch path, a `Makefile` `test` target and a vendored-copy `diff`. When the sibling repos are on local disk, it adds a cross-addon pass over the four collisions that only a same-session load of the whole collection exposes: slash tokens, vendored LibKa0s minors, vendored payload bytes and `## Interface:`. Each census is scoped to the TOC-derived load list and diffed against a recorded clean baseline instead of being re-derived. Findings rest on today's numbers, not on the committed `docs/test-cases.md` / `docs/automated-tests/RESULTS.md` / `docs/performance.md`, and the review says where those artifacts have gone stale. Fresh output goes to scratch. The agent never regenerates a committed report (that's release work) and never edits a test to change a result. A missing tool is a stated skip, never an inferred pass. Anything that needs a login is not run; it becomes the in-client checklist in `03_SMOKE_TESTS.md`. Measuring also opens new ground: unfalsifiable test cases (`testing-§12`), hand-maintained load lists where the TOC derivation is required, perf buckets no bracket reaches, and lint config that hides a real problem. Findings are graded by reachability, not by defect kind alone. Each one carries a `Reachability:` line saying who hits this, in what configuration, today. That line is written before the severity is chosen, and the severity buckets bind to it. Critical needs both a qualifying defect kind and a normal install that reaches it. A developer-only verb, a comment or a test-inventory-only defect cannot be High, whatever its kind. A degraded or fallback path is explicitly not capped: the cap depends on who reaches it, never on which branch it sits in. Before the bundle ships, the agent re-reads every `file:line` it cites, quotes the cited text beside it, reconciles figures across all five artifacts, and drops or corrects anything that does not resolve. Every count names the exact command and its scope. The agent vets its own findings and proposed changes against the living Ka0s WoW Addon Standard so remediation never introduces a new deviation. That is a guardrail, not a full audit (that's `standards-audit`), and if the standard can't be fetched it carries on and notes the skip. Vendored code (`libs/`, `tests/_kit/`) is read-only. A defect there is reported as an `[upstream]` finding to fix in the library repo and re-vendor, never a local patch. For subsystems the addon consumes from a shared library, the agent reviews the descriptor and the degradation stub rather than the library's implementation, and it never proposes re-hand-rolling what the library provides. Run it with `/wow-addon:review`. |
| `standards-audit` | A read-only compliance audit against the Ka0s WoW Addon Standard. It fetches the living `AUDIT.md` playbook and `standards/STANDARDS.md` (the standard's index) at runtime, follows the index's Sections list to fetch every section file, and measures the repository section by section and against the `anti-patterns` list. The result is a frozen `docs/audits/<YYYY-MM-DD>/` bundle: current state, deviations with stable IDs, evidence, remediation design and an execution plan. Before anything else it settles which rule set binds the repository, because the rotation holds three kinds of repo, not one. The eleven addons take the whole standard. `LibKa0s` takes `library-stack-§7`'s applicability list. The two documentation-and-tooling repos, `WowAddonStandards` and `wow-addon`, take the documentation lane. That lane has the same steps and the same artifacts, but it measures internal consistency between rules, cross-references that resolve, worked examples against the trees they cite, and inventories against the trees they count, and it grades on how far a defect reproduces rather than on who can reach it. Those two repos hold `AUDIT.md` and `agents/review.md`, the documents every other pass runs on. A defect in either was reproduced across twenty passes and reviewed by none until they entered the rotation. `Ka0sAddonsCommonTasks` is deliberately left out, since it is frozen planning bundles with nothing for a checklist to bind to. Deviations are graded by impact, not rule strength. High is reserved for what a user, their SavedVariables or their session can hit today, so a doc-only MUST failure is Low or Info and still names its MUST. Where several observations follow from a single unadopted subsystem, the audit files one root with `derived from <ID>` dependents and reports both the roots-only headline tally and the total. Before filing any MUST as open, it reads the recorded-deviation register: `docs/ARCHITECTURE.md` § Documented deviations, the repo's issue-audit GitHub issue store (read via `gh issue list` and keyed on the `state:` label), the root `CLAUDE.md` and `docs/scope.md`. A ratified row makes the gap a recorded deviation outside the MUST tally. A decline recorded only as a closed `state:will-not-do` issue, with no register row, is itself a `documentation-§3` deviation to file. It re-reads and quotes every `file:line` it cites before writing, reconciles figures across artifacts, and states each count's exact command and scope. The mechanical checks are run, not reasoned about. They are lint, the headless suite, a `diff -r` of every vendored Ka0s-owned library against its sibling source repo, and the complexity run, through the vendored runner's sighted suite. The `diff -r` uses the tag the addon's root `CLAUDE.md` provenance line names, not the sibling's `HEAD`: diffing against `HEAD` measures scheduling rather than compliance, and that drift is invisible to both repos' test suites. The provenance line's own placement is audited too. ### Hooks

- The line-ending hook normalizes files on Write, Edit and MultiEdit. When a file is written or edited inside a git repo, the plugin asks git what that file's `.gitattributes` declares and normalizes to it: CRLF in a client-bound Ka0s repo (the addons and `LibKa0s`), LF in one that ships nothing to the WoW client (the standards repo and this one). Every Ka0s repo declares one or the other (`line-endings`). The hook asks for `text` as well as `eol`, so a file marked `binary` is left alone even though the pin still answers `eol: crlf` for it (`line-endings-§7`). It is silent on files with no declared `eol` as well, and it never blocks a write. It lives at `hooks/hooks.json` + `scripts/normalize-eol.sh`.
- The bounded-runs hook keeps heavy runs on Bash in check. It is a `PreToolUse` hook that refuses an unbounded `lua tests/run.lua` / `lua tests/perf.lua`, `run-automated-tests.sh`, `luacheck` or `lizard`, and names the bounded runner to prefix instead: `~/.claude/wow-addon/bin/ka0s-bounded <command>`. That path is a symlink the hook keeps pointed at the installed `scripts/ka0s-bounded`. The plugin also ships `bin/ka0s-bounded`, a POSIX `sh` wrapper that `exec`s the runner, and Claude Code puts the plugin's `bin/` on PATH, so the bare `ka0s-bounded <command>` works too. The runner caps process memory (`ulimit -v`, `KA0S_KIT_PROC_MB`, default 2048), the process tree's memory and task count (a `systemd-run --user --scope`, `KA0S_KIT_TREE_MB` default half of RAM, `KA0S_KIT_TASKS` 256) and wall-clock time (`KA0S_KIT_TIMEOUT_S`, 900). It queues on a machine-wide `flock` slot pool (`~/.cache/ka0s-kit/slots`, `max(1, MemAvailable×0.6 / KA0S_KIT_SLOT_MB)` slots, or `KA0S_KIT_SLOTS`), so several repos' suites can run in parallel without exhausting memory. Exit codes pass through, and 124 (timeout) and 137 (killed) get a one-line explanation. Only a command in command position counts. The same words inside quotes or a heredoc body, such as a commit message or an `ANALYSIS.md` written with `cat <<'EOF'`, are prose and pass. Lua runs in a repo whose `tests/_kit` is LibKa0s kit revision 23+ are let through, because that kit bounds itself with the same variables. The hook exists because an unbounded runaway suite once OOM-killed a whole WSL2 VM and the session driving it. To opt out for one command, add an inline `KA0S_BOUNDED_HOOK=off` assignment.

## Install

Install it straight from this GitHub repo. You don't need to clone anything by hand. In any Claude Code session, run these three commands:

```
/plugin marketplace add tusharsaxena/wow-addon
/plugin install wow-addon@wow-addon
/reload-plugins
```

What each one does:

1. `/plugin marketplace add tusharsaxena/wow-addon` registers this repo as a plugin marketplace, and Claude Code clones it for you. You can also pass the full URL `https://github.com/tusharsaxena/wow-addon.git` or, if you already have a local clone, the path to it.
2. `/plugin install wow-addon@wow-addon` installs the plugin (`wow-addon`) from the marketplace (`wow-addon`). When it asks for a scope, choose **user** to enable it in every project on this machine, or **project** to enable it only in the current project.
3. `/reload-plugins` activates the plugin in the current session without a restart.

Once it is installed, the commands, the `review` and `standards-audit` subagents, the line-ending hook and the bounded-runs hook are available in every Claude Code session.

## Updating

When the repo changes (new commands, an updated agent, a new hook), pull the latest and reload:

```
/plugin marketplace update wow-addon
/reload-plugins
```
